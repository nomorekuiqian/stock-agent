# Lib - 共享工具库

## 功能概述

`src/lib/` 提供前端共享工具。认证相关代码在本轮回撤后已经重新简化，重点回到：

- `auth.ts` 只负责少量 auth 纯函数和 token 恢复
- `api.ts` 不再承担复杂恢复状态机
- `insforge.ts` 只负责创建 SDK client

## 核心文件

| 文件 | 职责 |
|------|------|
| `api.ts` | 统一 API 客户端，所有后端调用入口 |
| `auth.ts` | 登录、Google OAuth、token 获取、密码重置 |
| `auth-storage.ts` | localStorage auth token/user 存取与清理 |
| `auth-token.ts` | JWT 过期判断 |
| `auth-verification.ts` | `/verify-email` redirect 与 pending signup 状态 |
| `auth-redirect.ts` | 登录后的 redirect path 管理 |
| `insforge.ts` | Insforge SDK client |

## 认证架构

### `auth.ts`

当前 `auth.ts` 已回到简单链路：

```text
signIn()
  -> POST /api/auth { action: 'login' }
  -> syncClientAuthSession()

getAccessToken()
  1. 先读内存缓存
  2. 再读 sdk.getCurrentSession()
  3. 最后调 GET /api/auth/session
```

保留的兼容导出：

- `cleanupAuthCallbackUrlParams()`：仅做 URL 参数清理
- `consumeForcedReauthReason()`：现在固定返回 `null`
- `getAccessTokenResolution()`：只是对 `getAccessToken()` 的轻包装

这些兼容导出是为了降低回撤时的改动面，不代表系统仍然依赖旧的复杂恢复模型。

### `syncClientAuthSession()`

登录成功后会把 access token 同步到：

- 模块级缓存 `_cachedToken`
- SDK `httpClient`
- `localStorage`

这样后续业务请求能先走内存 / SDK，而不是每次都打 `/api/auth/session`。

### `clearStaleAuthStateWithoutRedirect()`

清理顺序：

1. 清 `_cachedToken`
2. 清 localStorage auth 数据
3. 清 SDK auth header
4. best-effort 调 `insforge.auth.signOut()`
5. `DELETE /api/auth` 清应用域名 cookie

## `api.ts`

`api.ts` 已经移除这些 auth 控制逻辑：

- 请求前轮询等待恢复
- `transient_failure` 这类三态判断
- 401 后自动 refresh 再重试
- forced reauth 错误编排

现在规则更简单：

- 需要登录的请求统一调用 `_authHeaders(..., { required: true })`
- `_authHeaders()` 只负责拿 token；拿不到就直接抛“登录已过期”
- `fetchProtected()` 不再帮你做额外恢复状态机

这让前端和后端的认证边界重新清楚起来：前端负责拿 Bearer token，后端负责验证 Bearer token。

## 注意事项

- `getAccessToken()` 依然必须检查 JWT `exp`，不能把“有 session 对象”当成“token 可用”
- 登录逻辑要继续使用 `/api/auth { action: 'login' }`，不要改成 SDK 直登
- 如果未来要增强 auth，优先扩 `GET /api/auth/session` 这一条恢复链，而不是重新引入多套 recovery 状态
- `signInWithGoogle()` 现在走 SDK/provider 默认 OAuth 流，不再依赖自定义 `oauth-exchange`
- `auth-verification.ts` 里的 pending signup 数据只服务注册体验，不应该反过来主导登录态恢复
