# Research - 研究台页面

## 页面概述

专业级 Stock Screener 前端页面，从 3,680+ 只可交易美股中通过预设策略和渐进式收窄筛选候选股。需要登录。

## 产品愿景

构建「自然语言 Agent + 预设策略 + 智能收窄」三位一体的股票筛选体验，并作为统一研究台的起点。用户可通过自然语言描述或预设策略入口快速缩至 ~30 只，再逐步收窄到 3-5 只候选。选股完成后，右边面板可直接切换到个股研究、日报、宏观等内容（不跳页），左边 Agent 保持 context 继续对话。详见 `docs/plans/research-desk.md`。

## 架构

两阶段 UI：WelcomeScreen（入口）→ 左右分屏研究台（Chat + Content）。

```
/research (page.tsx, CSR, PaywallGuard)
    |
    v
phase === 'welcome'
    |
    v
WelcomeScreen -- 左右分屏布局
    左: 品牌 M logo + 标题 + 描述 + 统计 + 历史对话列表 (desktop)
    右: 4 策略卡片(2x2) + 主题 chips + 聊天输入框 + 历史对话 (mobile)
    |
    v (用户选策略/输入消息)
    |
phase === 'chat'
    |
    v
固定分屏研究台 (top-16 bottom-0)
    顶栏: "重新开始" + DataStatus(inline) + 保存状态
    左半: ChatPanel (消息列表 + 输入框, Agent 固定)
    右半: ContentPanel (普通 Research 动态内容面板, 支持栈式导航)
        ├── type='screener': ResultsPanel (漏斗 + 条件 + 候选列表)
        └── type='stock': StockResearchView (嵌入式个股研究)
        KOL 模式: KolChunksPanel (博主历史推文引用，不用 agent navigate 切换面板)
    移动端: MobileTabSwitch 切换 chat/results
```

### Chat Layout Invariant

Chat 阶段外层固定在 `top-16 bottom-0`，左侧 `research-chat-shell`
必须保持 `scrollTop=0`。长对话只能滚动 `ChatPanel` 的消息列表
(`research-chat-scroll`)，不能让左侧 shell 或 document 滚动；否则切换长短
conversation 时历史侧栏会随祖先滚动发生垂直位移。

## 数据流

### Research Agent 对话路径 (主要)
1. 用户在 WelcomeScreen 选择策略卡片或直接输入 → `handleSend(message)`
2. `dispatch({ type: 'SEND_MESSAGE' })` → `isLoading: true`, `phase: 'chat'`
3. `api.research.chatStream({ message, history, accumulated_filters, conversation_id, active_context })` → Research Agent 处理
4. 响应成功 → `dispatch({ type: 'RECEIVE_RESPONSE', result })` → 更新消息、候选、漏斗
5. 如果本轮有新候选/推荐、`reset_results` 或 `navigate.type === 'screener'` → 右侧强制切回 screener 结果面板；否则才按 `result.navigate` 切到 stock/report/macro/brew。这样筛选消息不会因为中途查了 AMD/NVDA 工具而停在个股面板。
6. 自动保存对话 (含 content_stack 状态) → `POST/PUT /api/screener/conversations`。保存 payload 使用本轮导航后的 `active_content` / `content_stack`，避免第一轮显示已切回 screener 但持久化仍保存旧 stock 面板。
7. 用户继续对话或点击 option chips → 累积条件，重复 2-6

### 个股研究路径 (Research Desk)
1. 用户点击候选列表中的股票 → `handleStockClick(symbol)`
2. `dispatch({ type: 'PUSH_CONTENT' })` → contentStack 压入 screener，activeContent 切换到 stock
3. ContentPanel 渲染 StockResearchView → 加载行情/基本面/AI 分析 (AI 分析自动触发)
4. StockResearchView 数据就绪 → `onContextReady(payload)` → stockContextRef 更新
5. 用户可点击"深度研究"跳转 `/stock/{symbol}` 或"加入持仓"添加到 watchlist
6. 用户在 ChatPanel 继续对话 → API 请求携带 `active_context`（含行情/基本面/财报/技术面/近期新闻）
7. Agent 基于 stock context 回答问题
8. 用户点击"返回选股" → `dispatch({ type: 'POP_CONTENT' })` → 回到 screener 视图

嵌入式个股财报面板 (`PanelEarningsTab`) 复用 `/api/stocks/{symbol}/earnings-data`，用 income statement 作为季度选择权威来源；EPS surprise 由后端在 yfinance 滞后时通过 FMP earnings-calendar 兜底。

嵌入式个股 Market 面板 (`PanelMarketTab`) 复用 Market Tab 的精简结构：`market-overview` KPI + `news-feed` + `press-releases`。旧分析师评级、市场热度、同行比较子 Tab 已移除，active_context 不再携带 `analyst_summary`。

普通 Research 与 KOL 发送路径共用 `page.tsx` 的 active context 构建逻辑。
KOL 请求把该上下文作为 `content_context` 传给
`/api/kol_research/chat/stream`，用于让 `input_guard.py` 理解「这只股票」
这类短追问；如果完整 stock 面板数据尚未 ready，至少会从
`activeContent.params.symbol` 传递 `{ type: "stock", symbol }`。KOL 模式右侧
仍以 `KolChunksPanel` 展示过往推特证据为主，不消费 agent `navigate` 切换内容面板。

### 对话恢复路径
1. WelcomeScreen 加载 → `useInfiniteQuery(queryKeys.research.conversations(userId, 20))` 获取历史；Query key 按 `userId` 隔离，10min fresh / 60min gc，并用 `localStorage research_conversations_cache_v1:{userId}` 做 60min 首屏缓存
2. 用户点击历史对话 → 先尝试 `api.research.conversations.get(id)` 读取 picker 兼容层的完整业务状态（filters/candidates/recommendations/funnel/KOL chunks/persona）
3. 基于 picker data 的 `persona_username` 推断 runtime `agent_id`，再调用 `api.agentRuntime.getSession(id, agent_id)` 读取 durable 消息和 `ui_state`
4. 如果 picker row 缺失，先按默认 `research_agent` 查 runtime；没有结果时再试 `kol_research_agent`，并用 runtime metadata 的 `persona_username` 恢复 KOL 模式
5. `dispatch({ type: 'LOAD_CONVERSATION' })` → runtime 消息和 `ui_state` 优先，picker 业务状态补齐 → `phase: 'chat'`

恢复过程必须避免把临时 loading / runtime-only 状态自动保存回
`picker_conversations`。`handleLoadConversation()` 会用 `loadingConversationRef`
暂停 mount-time runtime reconciliation；任何 reconciliation dispatch 前也会设置
`skipPanelSaveRef`，防止恢复出的消息覆盖 picker 里的
`accumulated_filters` / `candidates` / `recommendations` / `funnel_steps`。

### KOL Persona Welcome 模式

当 URL 或 PersonaSelector 进入 `agentKind === 'kol_research'` 且 `personaUsername` 存在时，WelcomeScreen 渲染 qinbafrank 专属 Landing：

- **首屏定位**：保持原有居中头像 + @handle 的简洁样式，减少说明性文案。
- **Quote 口径**：使用多条 @qinbafrank 原文短句展现物理 AI、定价观、产业观、宏观观和风控观；桌面完整呈现，移动端只露出前两条，避免把提问入口推到首屏之外。
- **Quick Actions**：使用一个统一的 qinbafrank Lens 面板承载三类问题入口。桌面为非等高布局：股票和行业在左列，市场问题在右列；移动端按股票、市场、行业顺序堆叠。
- **二层输入**：股票卡直接展示 ticker / 公司名输入；市场卡直接展示大盘风险、流动性、行情主线、财报季四个选项并支持自定义变量；行业卡直接展示产业链输入框。不再需要点击卡片后展开，也不展示热门 chip。
- **发送口径**：二层卡片不在前端展示完整 prompt，但发送给 KOL Agent 时会补齐「按 qinbafrank 框架」「过去是否直接提到」「当前数据支持或证伪」「关注哪些公司和风险信号」等上下文，避免用户只点短 chip 后问题过泛。

KOL 专属页深链用 `/research?agent=kol&persona=qinbafrank&q=...`。`page.tsx` 会在 URL 进入时切到 `kol_research`、设置 persona，并把 `q` 作为第一轮问题直接发送给 KOL Agent。旧的 `symbol=` 但无 `q` 链接会兜底生成「按 qinbafrank 的框架分析该标的」的问题，避免用户落到空对话后再手动输入。

有 `q` 的 KOL 深链必须先 `RESET`，再写回 `personaUsername`，否则 `RESET`
会清掉 persona，seed 问题会误走普通 Research Agent 的
`/api/research/chat/stream`。

硬刷新同一个 KOL 深链时，`sessionStorage` 可能已经恢复出同 persona、同第一轮
user message 的会话。此时 URL seed effect 必须只标记 signature 已处理，不能再
`RESET` 或重新发送 `q`，否则会创建重复 KOL conversation 并让侧栏出现同题双条。

KOL 追问的 `kol_chunks` 是右侧「原文支持」面板的数据缓存。若某一轮 follow-up
没有返回新的 `kol_chunks`，前端必须保留上一轮 chunks，不能把已保存证据覆盖成
空数组；否则恢复旧对话时右侧面板只剩占位文案。KOL conversation 也不要保存默认
`SCREENER_CONTENT` 到 `active_content`，除非用户/Agent 明确切到 stock、macro 等
真实内容面板。

## 认证与额度

Research 对话端点支持匿名访问，但前端在 `useAuth` hydration 完成后才展示页面。额度规则由后端 `/api/research/quota` 和 `/api/research/chat[/stream]` 统一执行：

- Anonymous / Free / Pro: 每日 5 次。
- Max (`ai_research_engine` entitlement) / lifetime: unlimited。
- `/research/page.tsx` 查询 quota 时等待 `authLoading` 和 `SubscriptionContext` 完成；如果前端已识别为 Max，直接显示 unlimited。
- 已登录用户发送 Research Agent 请求时要求 `Authorization` token 存在，避免 token 恢复短暂失败时被后端按 anonymous/IP 额度计数。

## 对话状态管理 (researchReducer)

`useReducer` + `sessionStorage` 持久化。关键状态:
- `phase: 'welcome' | 'chat'` — 页面阶段
- `messages: Message[]` — 对话历史 (user/assistant, 含 options)
- `isLoading: boolean` — Agent 请求中 (loadState 强制 false 防止刷新后卡住)
- `accumulatedFilters` — 累积筛选条件
- `candidates` / `candidateCount` / `universeSize` — 筛选结果
- `funnelSteps` / `recommendations` — 漏斗和选股理由
- `conversationId` / `conversationTitle` — 对话持久化标识
- `hasNewResults` — 移动端 results tab 新结果指示
- `activeContent: ContentContext` — 当前右侧面板内容 (screener/stock/...)
- `contentStack: ContentContext[]` — 内容导航栈 (支持 PUSH/POP/SWITCH)

页面级状态 (在 `page.tsx` 中独立 `useState`，不在 reducer 内):
- `agentKind: 'research' | 'kol_research'` — 当前对话使用的 Agent 类型
- `personaUsername: string | null` — KOL 模式下选中的博主用户名
- `handleKolSend(message)` — KOL 路径专用发送函数，调用 `api.kolResearch.chatStream()` 处理 SSE 事件流

## Research 对话持久化

- **自动保存**: 每轮 `/api/research/chat/stream` 完成后，前端异步调 POST/PUT conversations API
- **状态**: `researchReducer` 新增 `conversationId` + `conversationTitle`
- **恢复**: WelcomeScreen/侧栏显示最近 20 条对话并支持继续加载，点击触发 `LOAD_CONVERSATION` action
- **删除**: 历史列表 hover 显示删除按钮
- **title**: Agent 每轮生成 (5-10 中文字)，反映选股方向
- **侧栏列表缓存**: `/api/research/conversations` 首屏分页由 React Query 无限列表缓存，SPA 内返回 `/research` 不重复请求；同时写入用户隔离的 `localStorage`，刷新后先展示缓存并在过期后后台刷新。新建/更新/删除对话会同步更新 Query 缓存，避免等下一次 list 请求。
- **Agent Runtime sidecar**: 普通 research 请求会把稳定 `conversationId`
  作为 `conversation_id` 传给 `/api/research/chat/stream`。新对话第一轮会先
  在前端预分配 UUID，回合结束后创建 `picker_conversations` 时也使用同一个 id。
  后端据此写 `agent_sessions(agent_id=research_agent, metadata.agent_kind=research)`
  和 `agent_session_events`，避免 runtime 产生无法关联 UI 的随机 session。
  conversation save payload 中的 `active_content` / `content_stack` 会同步到
  `agent_sessions.metadata.ui_state`，同时写 `ui_navigation` event；tool/error/context
  timeline 由后端在流式回合内写入 runtime events。
- **Runtime 恢复优先级**: 恢复时 runtime 的 `entries` 覆盖 picker 保存的
  `messages`，runtime 的 `ui_state` 覆盖 picker 的 `active_content` /
  `content_stack`。picker 仍负责补齐 runtime 暂未承载的筛选结果、推荐、漏斗和
  KOL chunks。若 picker 缺失，`handleLoadConversation()` 会 fallback 到另一个
  agent id，并通过 runtime metadata 恢复 `persona_username`。
- **面板状态保存去重**: 右侧 `active_content` / `content_stack` 的后台保存只在
  面板内容签名变化后触发。刷新、auth hydration、React Query key/userId 变化或
  `saveConversation` callback 重新创建，不能把未变化的已恢复会话重新 PUT，也不能
  touch `updated_at` 或把侧栏排序推到顶部。

## 注意事项

- tvscreener 板块名称是英文（如 "Technology Services"），需要用 `SECTOR_ZH` 映射显示中文
- symbol 格式可能带交易所前缀（如 "NASDAQ:AAPL"），显示和跳转时需要 strip
- ChatInput 已处理 IME 输入法兼容 (`e.nativeEvent.isComposing` 检查)，防止中文输入法 Enter 误触发提交
- `getAccessToken()` 内部对 SDK session 读取有 2 秒超时保护，并在 Server Proxy refresh 失败时做短重试，防止 SDK 挂起或短暂抖动直接把用户踢回登录页
- Screener 页面现在通过共享 auth error helper 识别“已过期”与“临时认证失败”，统一提示用户先 `Command + Shift + R` 刷新；如果仍失败，再手动退出登录后重试
- Agent 请求前会压缩 history：history 只包含过去上下文，当前用户问题只走 `message` 字段；过滤 error/streaming 消息，中性 research 最多发送最近 24 条历史，KOL 最多 20 条历史，单条历史最多 2000 字。
- 140 秒安全超时: `page.tsx` 中 isLoading 超过 140 秒自动 SET_ERROR 恢复；正常流式请求由 `api.ts` 的 135 秒 fetch timeout 先处理，避免 UI 早于 API 判失败。
- 对话保存的 stale closure 陷阱: `handleSend` 中 `state.messages` 是 SEND_MESSAGE dispatch 之前的快照，保存时需手动构造 userMsg 包含在 payload 中

## Debugging KOL chat failures

KOL chat failures are intentionally split into explicit frontend messages
instead of one generic "AI 助手暂时无法响应". `getAgentErrorMessage()` maps
backend / client codes to user-safe text:

- Backend SSE codes: `agent_timeout`, `context_too_long`,
  `model_schema_error`, `agent_setup_error`, `agent_error`
- Client-side codes: `auth_error`, `http_error`, `client_timeout`,
  `network_error`, `stream_no_final`

To debug a failing turn, walk these four checkpoints in order; the first that
does NOT show a matching signal is the failure point.

1. **Network tab** — `POST /api/kol_research/chat/stream` with status `200` and
   `text/event-stream` content type. If missing, the frontend never sent the
   request (check the URL-driven KOL effect in `page.tsx` — `lastProcessedKolUrl`
   ref skips re-fire, the `signature` may collide).
2. **Console (frontend)** — search for these instrumentation lines:
   - `[KOL Research] backend error event:` — backend yielded an `error` SSE
     event or `api.kolResearch.chatStream()` synthesized one from a non-2xx
     HTTP response / client timeout / network failure. Object includes `code`,
     optional `status`, optional `detail`, and raw `error` text.
   - `[KOL Research] no final event — stream closed cleanly without answer` —
     SSE finished without `final`. Most often: dev StatReload mid-stream, or
     stream-side `return` that skipped `final`.
   - `[KOL Research] handleKolSend error:` — exception in the fetch / parse
     layer (network drop, JSON syntax error in SSE).
3. **Backend access log** — `tail -f /tmp/uvicorn-frank.log`. Look for
   `POST /api/kol_research/chat/stream 200 NNNms`. Missing line = middleware
   rejected (feature flag `kol_research_agent`, auth, CORS).
4. **Agent log** (same file) — `kol chat request: persona=X message=... ` is
   logged at the top of `stream_kol_research`. Failure produces
   `kol chat failed: persona=X elapsed=Ys code=Z err=...` with full traceback
   via `logger.exception`.

**Common dev-loop gotcha**: `uvicorn --reload` restarts on any `*.py` change.
If a file is saved while a chat stream is open, the worker is killed and the
SSE connection closes mid-flight → checkpoint 2 logs "no final event" and the
backend log shows no error (because the worker never reached the error path).
Save files **between** turns or run uvicorn without `--reload` for reliable
chat testing.
