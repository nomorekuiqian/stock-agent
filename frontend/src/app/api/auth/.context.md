# Auth API Route - 当前状态

## 当前情况

`/api/auth` 目录目前**没有** `route.ts`。当前认证体系完全走 `@insforge/sdk` 客户端直接调用，不经过 Next.js Server Route。

目录内容：
- `.context.md` (本文件)
- `oauth-callback/` (空目录)
- `session/` (空目录)

## 当前认证架构（SDK Direct）

认证逻辑在 `frontend/src/lib/auth.ts`，直接调用 `@insforge/sdk`：

- 邮箱密码登录 → `insforge.auth.signInWithPassword()`
- Google OAuth → `insforge.auth.signInWithOAuth()` + `insforge.auth.getCurrentUser()`
- Session 读取 → 模块级缓存 → SDK tokenManager → `insforge.auth.refreshSession()`
- 登出 → `insforge.auth.signOut()`

路由保护：`middleware.ts` 检查 `insforge_csrf_token` cookie（first-party，由 SDK 在登录时写入我们域名）。

## 已知局限

`insforge_refresh_token` 是 Insforge 服务器通过 `Set-Cookie` 设置在 **Insforge 域名**上的 cookie。从我们域名发起的请求属于跨域请求，以下场景会导致 refresh 失败、刷新页面后登录状态丢失：

- Chrome 无痕模式（默认阻止第三方 cookie）
- Safari（默认 ITP 策略阻止）
- Firefox（Enhanced Tracking Protection 可能阻止）

## 未来：Server Bridge（待实现）

彻底解决刷新后登录丢失的方案是实现 `/api/auth/route.ts`：

- Server-side 调用 Insforge 登录 API，从 `Set-Cookie` 响应头提取 refresh token
- 将 access/refresh token 存为我们域名下的 **httpOnly first-party cookie**
- `GET /api/auth` 在 server side 刷新 token，客户端无需直接访问 Insforge 域名
- middleware 检查 first-party cookie，刷新页面后仍能恢复 session

实现此 Server Bridge 之前，刷新页面后的 session 恢复依赖 Insforge 域名的第三方 cookie，在无痕/部分浏览器下不可用。

## 注意事项

- 不要引入 `@insforge/nextjs`
- Server Bridge 实现后，`lib/auth.ts` 的 SDK Direct 调用应迁移到走 `/api/auth`
- `lib/.context.md` 和 `contexts/.context.md` 描述的是当前 SDK Direct 现状
