# Auth API Route - Server Proxy 认证路由

## 功能概述

`/api/auth` 是认证的 Server Proxy 层，解决 Insforge SDK 跨域 cookie 问题：

- `POST { action: 'sign-in' }`：Server Proxy 登录。服务端调用 Insforge 登录 API，从 Set-Cookie 响应头提取 refresh token，存储为我们域名的 httpOnly cookie。这是登录的**主链路**（SDK 直接登录无法在我们域名存储 refresh token）
- `POST { action: 'refresh' }`：Server Proxy 刷新。读取我们域名的 refresh cookie，转发给 Insforge 换新 access token
  - refresh 成功后还会同步更新本域名下的 refresh / csrf cookies，避免 refresh token 或 csrf 轮换后下一次恢复失败
- `POST { action: 'verify-email' }`：代理邮箱验证码/链接验证，成功后把 access token、refresh token、csrf token 一起桥接回我们域名 cookie
- `POST { action: 'oauth-exchange' }`：代理 Google OAuth code exchange，避免 callback 直接落受保护页时被 middleware 抢先重定向，同时把 refresh token 桥接回我们域名 cookie
- `POST { action: 'bridge-session' }`：校验一个已有 access token，并把 session/user/csrf 同步到我们域名 cookie。用于 SDK 直连拿到 session 后补齐 first-party cookie
- `DELETE`：在 SDK 清理基础上，额外删除所有 auth cookies

## 文件

| 文件 | 职责 |
|------|------|
| `route.ts` | Server Proxy 登录/验证/OAuth exchange/刷新/bridge-session/清 cookie |

## 端点

| 方法 | 路径 | 功能 |
|------|------|------|
| `POST` | `/api/auth` | `action=sign-in` / `refresh` / `verify-email` / `oauth-exchange` / `bridge-session` |
| `DELETE` | `/api/auth` | SDK 清理认证态 + 清除所有 auth cookies |

## 登录流程

```
AuthContext.handleSignIn(email, password)
  → POST /api/auth { action: 'sign-in', email, password }
    → Server: POST Insforge/api/auth/sessions
    → 提取 Set-Cookie 中的 refresh token
    → 设置我们域名的 cookies (session, user, refresh, csrf)
    → 返回 { accessToken, user, csrfToken }
  → 前端同步 accessToken 到 localStorage + SDK httpClient
  → AuthContext.setUser(user) 更新 React 状态
```

## OAuth / Verify Email 桥接

```
Google OAuth
  → AuthContext.signInWithGoogle()
  → redirectTo 固定指向 /auth/callback (公开路由)
  → callback 页把 insforge_code + PKCE verifier 发给 POST /api/auth { action: 'oauth-exchange' }
  → Server Proxy 调 Insforge /api/auth/oauth/exchange
  → 提取 Set-Cookie refresh token，写回我们域名 cookies

邮箱验证
  → AuthContext.verifyEmail()
  → POST /api/auth { action: 'verify-email', otp, email? }
  → Server Proxy 调 Insforge /api/auth/email/verify
  → 提取 Set-Cookie refresh token，写回我们域名 cookies
```

## 管理的 Cookies

| Cookie 名 | 内容 | 用途 |
|-----------|------|------|
| `insforge-session` | access token | SSR 认证 |
| `insforge-user` | 用户 JSON | SSR 用户数据 |
| `insforge-refresh` | refresh token | Server Proxy 刷新 |
| `insforge_refresh_token` | refresh token (兼容) | 旧格式兼容 |
| `insforge-csrf` | CSRF token | 刷新请求验证 |
| `insforge_csrf_token` | CSRF token (client-readable) | SDK 兼容 / CSRF 轮换同步 |

## 注意事项

- 登录必须通过 Server Proxy（`action=sign-in`），不能用 SDK 直接登录。原因：SDK 登录时 Insforge 的 refresh token 设在 Insforge 域名的 cookie 上，跨域 SameSite 策略阻止我们读取
- OAuth callback 不能直接回受保护页。现在统一先回 `/auth/callback`，完成 code exchange 和 cookie bridge 后再跳转到最终页面
- 邮箱验证成功也必须经过 Server Proxy，不能只依赖 SDK 本地 session；否则 middleware 和 `/api/auth refresh` 看不到同一份 first-party cookie
- 代理转发到 Insforge `/api/auth/sessions` 和 `/api/auth/refresh` 时，需要同时带 `Authorization: Bearer <anonKey>` 与 `apikey: <anonKey>`，保持和服务端校验接口一致
- `bridge-session` 会用 `GET /api/auth/sessions/current` 复核 access token，再写入 `insforge-session` / `insforge-user` / `insforge-csrf`，避免前端伪造用户 cookie
- production 当前 canonical host 是 `www.themarketbrew.com`，而裸域会先跳转过去；为避免 host 切换导致 auth cookie 分裂，route handler 现在会把 auth cookies 统一写到 `.themarketbrew.com`
- refresh token 提取不能只依赖 `headers.getSetCookie()`；当前 route 也兼容读取 `set-cookie` 原始头，降低 serverless/runtime 差异带来的线上丢 cookie 风险
- `handleRefresh()` 现在会把新的 `csrfToken` 同步回 `insforge-csrf` 和 `insforge_csrf_token`。否则一旦上游 refresh/CSRF 轮换，本域名继续保留旧 CSRF 值，后续 refresh 可能稳定失败
- 页面鉴权和接口鉴权分离，后端业务接口仍要自己做 `verify_user_token`
