# Auth API Route - SDK 认证路由

## 功能概述

`/api/auth` 以 SDK handler 为主，但项目额外包了一层最小自定义逻辑：

- `POST { action: 'refresh' }`：把当前域名上的 refresh cookie 转发给 Insforge，换取新的 access token
- `POST { action: 'refresh' }` 会兼容读取 `insforge-refresh` 和旧的 `insforge_refresh_token`
- `DELETE`：在 SDK 清理基础上，额外删除项目自己写入的 auth cookies，避免旧状态残留

## 文件

| 文件 | 职责 |
|------|------|
| `route.ts` | 导出 SDK 的 `POST/GET/DELETE` handlers |

## 端点

| 方法 | 路径 | 功能 |
|------|------|------|
| `POST` | `/api/auth` | SDK 保存/同步认证态；`action=refresh` 时刷新 access token |
| `GET` | `/api/auth` | SDK 查询当前认证态 |
| `DELETE` | `/api/auth` | SDK 清理认证态，并额外清掉自定义 auth cookies |

## 协作关系

认证恢复依赖这几层一起工作：

1. `frontend/src/app/api/auth/route.ts`
2. `frontend/middleware.ts`
3. `frontend/src/app/layout.tsx` 的 `auth()`
4. `frontend/src/components/Providers.tsx` 的 `InsforgeBrowserProvider`
5. `frontend/src/contexts/AuthContext.tsx`

## 注意事项

- 这里不是旧文档里的“server proxy 登录入口”
- 这里已经不只是简单 passthrough；`refresh` 和强制清理旧 cookie 是前端兼容旧会话的关键兜底
- 页面鉴权和接口鉴权分离，后端业务接口仍要自己做 `verify_user_token`
