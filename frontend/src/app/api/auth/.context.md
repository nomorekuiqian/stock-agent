# Auth API Route - Server Proxy 认证路由

## 功能概述

当前 `/api/auth` 已回撤到更简单的结构：

- 自定义部分只保留 `POST { action: 'login' }`
- 其余认证 GET / POST / DELETE 交给 `@insforge/nextjs/api` 的 `createAuthRouteHandlers()`
- 独立的 `GET /api/auth/session` 负责 access token 校验与 refresh 恢复

这里的关键职责不是“承载整套 auth 状态机”，而是解决浏览器跨域 cookie 无法直接桥接的问题。

## 文件

| 文件 | 职责 |
|------|------|
| `route.ts` | 旧式 login proxy + 默认 auth route handlers |
| `helpers.ts` | cookie options、失效 cookie、refresh token 提取 |
| `session/route.ts` | 校验 session cookie，并在需要时用 refresh token 换新 access token |

## 端点

| 方法 | 路径 | 功能 |
|------|------|------|
| `POST` | `/api/auth` | `action=login` 时走自定义登录代理，其余 POST 交给默认 handler |
| `GET` | `/api/auth` | 默认 handler |
| `DELETE` | `/api/auth` | 默认 handler + 清理本域 auth cookies |
| `GET` | `/api/auth/session` | 校验或恢复当前会话 |

## 登录流程

```text
POST /api/auth { action: 'login', email, password }
  -> 服务端调用 Insforge /api/auth/sessions
  -> 从 Set-Cookie 提取 refresh token
  -> 写入 insforge-session / insforge-refresh / insforge-csrf
  -> 返回 accessToken + user
```

这条链路必须保留。原因是 Insforge 登录返回的 refresh token 在 `Set-Cookie` 头里，前端跨域 fetch 不能直接把它稳定转成应用域名下的 first-party cookie。

## `/api/auth/session`

`GET /api/auth/session` 是当前唯一的 cookie recovery 入口：

```text
1. 先读 insforge-session
2. 用 /api/auth/sessions/current 校验 access token
3. access token 无效时，再用 insforge-refresh + insforge-csrf 调 /api/auth/refresh
4. 刷新成功后重新写回 session / refresh / csrf cookies
5. 全部失败则清理失效 cookies，并返回 authenticated=false
```

这个路由服务于两类场景：

- 页面刷新后，SDK 尚未恢复出 user
- `getAccessToken()` 从 SDK 拿不到可用 token，需要从 cookie 补回

## Cookie 管理

当前主要管理这些 cookie：

- `insforge-session`
- `insforge-refresh`
- `insforge-csrf`
- `insforge-user`（清理兼容）

生产环境会继续把 cookie domain 写成 `.themarketbrew.com`，避免 `themarketbrew.com` 与 `www.themarketbrew.com` 之间出现双份登录态。

## 注意事项

- 不要再把 `verify-email`、`oauth-exchange`、`bridge-session` 这类动作重新塞回 `/api/auth`
- 登录主链路仍然必须经过 Server Proxy；SDK 直登无法把 refresh token 桥接到应用域名
- `DELETE /api/auth` 之后要同时清掉我们补写的 cookie，不能只依赖默认 handler
- `session/route.ts` 里 access token 校验和 refresh 都需要带 `apikey` / `Authorization: Bearer <anonKey>`
- `extractRefreshToken()` 不能只依赖单一 runtime API，保留对 `Set-Cookie` 读取差异的兼容处理
