# Contexts - React Context Providers

## 功能概述

全局状态通过 React Context 提供，挂载在 `components/Providers.tsx` 中。

当前认证体系走 first-party httpOnly cookie 的 server bridge：

- `Providers.tsx` 不再包 `InsforgeBrowserProvider`
- `AuthContext` 成为唯一前端 auth 状态源
- 登录/注册/邮箱验证通过 `frontend/src/app/actions/auth.ts` server actions 调 Insforge SDK
- OAuth code exchange 在 `frontend/src/app/auth/callback/route.ts` 服务端完成
- Session 恢复通过 `GET /api/auth/session`
- 路由保护由项目自定义 `frontend/middleware.ts` 完成（只检查 `app_access_token` / `app_refresh_token` 是否存在）

## 文件

| 文件 | 职责 |
|------|------|
| `AuthContext.tsx` | 认证状态、登录/注册/验证邮箱/登出、登录后用户同步 |
| `SubscriptionContext.tsx` | 订阅状态与支付入口 |
| `EntitlementsContext.tsx` | 当前用户 entitlement 集合、`has(feature)` 判断、默认 fresh 读取与 `refresh({ fresh })` 强刷 |

## AuthContext

### 提供的值

```typescript
{
  user: User | null,
  isLoading: boolean,
  isAuthenticated: boolean,
  setAuthenticatedUser: (user: User | null) => void,
  signIn(email, password): Promise<AuthActionResult>,
  signUp(email, password, name?, redirectPath?): Promise<SignUpResult>,
  signOut(): Promise<AuthActionResult>,
  signInWithGoogle(): Promise<AuthActionResult>,
  updateProfile({ name }): Promise<AuthActionResult>,
  resendVerificationEmail(email): Promise<AuthActionResult>,
  verifyEmail(otp, email?): Promise<AuthActionResult>,
  refreshUser(): Promise<void>,
}
```

### 状态来源

启动流程：

```text
mount
  -> AuthContext 调 fetchSession()
  -> GET /api/auth/session
  -> route handler 读取 app_access_token / app_refresh_token
  -> access token 有效则 getCurrentUser()
  -> access 缺失或失效时用 refresh token refreshSession()
  -> 返回 { user, accessToken }
  -> AuthContext setUser / setIsLoading(false)
```

不依赖：
- `useInsforge()`
- `sdk.isLoaded`
- `sdk.reloadAuth()`
- 浏览器直连 Insforge refresh cookie

### 登录

邮箱密码登录：
- `signIn()` → `signInAction()` server action → `insforge.auth.signInWithPassword()`
- 成功后 server action 写入 `app_access_token` / `app_refresh_token`，`AuthContext` 缓存 access token 并 `setUser(result.user)`

Google OAuth：
- `signInWithGoogle()` → `startOAuthAction()` server action → `insforge.auth.signInWithOAuth({ provider: 'google', redirectTo: '/auth/callback' })`
- 浏览器跳转到 Google 授权页
- 回跳 `/auth/callback` → route handler 读取 `app_oauth_cv` PKCE verifier → `exchangeOAuthCode()`
- 服务端写入 auth cookies 后跳回原 redirect

### 注册与邮箱验证

- `signUp()` → `signUpAction()` server action → `insforge.auth.signUp()`
- 需要验证邮箱时返回 `requiresEmailVerification`，跳转 `/verify-email`
- `verifyEmail()` → `verifyEmailAction()` server action → `insforge.auth.verifyEmail({ otp, email })`
- 验证成功后 server action 写入 auth cookies，`AuthContext` 缓存 access token 并 `setUser(result.user)`

### 登出

1. `signOutAction()` server action 读取当前 cookie access token 并尝试 `insforge.auth.signOut()`
2. 不论 Insforge signOut 是否成功，都清 `app_access_token` / `app_refresh_token`
3. 清 `AuthContext` user 和模块级 `_cachedAccessToken`
4. `queryClient.clear()`

## SubscriptionContext

`SubscriptionContext` 没有因为本轮 auth 改造改变职责，仍然：

- 依赖 `AuthContext`
- 负责订阅状态、checkout、billing portal
- 通过 `getAccessToken()` 为付费接口补 Bearer token
- subscription status 的 React Query key 必须按 `user.id` memoize，避免依赖它的 refresh callback 在每次 render 改变引用并触发重复 refetch。
- 默认请求 `subscription-status?fresh=true`，因为 pricing/profile/portal 回跳等订阅决策页必须绕开后端 5 分钟进程缓存，以 Stripe 为准。
- `createCheckout(product, returnPath, { billingInterval: 'monthly' })` 正式支持 `pro`、`max` 两个 checkout product；当前只发送 monthly。没有活跃付费订阅的用户走 Stripe Checkout；已有 Pro 订阅的用户升级 Max 时走 Billing Portal subscription update confirm，避免重复创建第二个订阅。
- `openBillingPortal({ returnPath, product })` 可打开普通订阅管理，也可由 `createCheckout()` 用于 Pro→Max 升级。
- `SubscriptionContext` 暴露 `/subscription-status` 返回的真实 Stripe Price 字段：`stripePriceId`、`billingAmountCents`、`billingCurrency`、`billingInterval`、`billingIntervalCount`。已订阅用户续费价格展示应使用这些字段，而不是按 `plan` 套当前公开价格。
- `cancelSubscription()` 调用 `POST /api/payment/cancel-subscription`，用于不打开 Stripe Portal 的自助取消。该路径支持 Stripe 账户迁移期的旧账户 fallback；调用成功后会更新 React Query cache 中的 cancellation 字段。
- `SubscriptionContext` 也透出 `stripeAccountRef` / `stripeMigrationState`，仅用于诊断和迁移流程，不应作为前端权限判断依据。
- Stripe Checkout success_url 会带 `checkout=success&tier=...`，所以回跳页和
  `SubscriptionContext` 都能识别 checkout return；成功页负责最终等待
  `subscription-status?fresh=true` 与 `me/entitlements?fresh=true` 同时生效后再跳转
- 服务端返回的 legacy `plan="ultra"` 会在 context 内 normalize 为 `plan="max"` 展示；`isPro` 对 Pro/Max 为 true，`isMax` 对 Max 为 true，不再暴露 `isUltra`。
- Profile 订阅展示直接使用 API 返回的 `plan/status/access_expires_at/cancel_at_period_end/cancel_at` 计算，不使用
  `isPro/isMax`，因为后者会受 `NEXT_PUBLIC_ENABLE_PAYWALL=false` 影响；功能权限仍使用
  `EntitlementsContext`
- Stripe Portal 周期末取消后订阅仍可能是 `status="active"`；`cancel_at` 是 pending-cancel 的主要展示信号，Profile 应显示“已取消 / 权益有效至”，不能等到 `status="canceled"`。
- `status="active"` 和 Stripe `status="trialing"` 都代表 active access display；实际功能仍以
  `EntitlementsContext` / 后端 `has_entitlement()` 为准。

## EntitlementsContext

- 依赖 `AuthContext` 的登录状态
- 默认请求 `GET /api/payment/me/entitlements?fresh=true`
- 暴露 `has(feature)` 给 `PaywallGuard`、Profile 邮件偏好等前端 gate 使用
- `refresh({ fresh: true })` 会旁路后端 5 分钟订阅缓存；checkout 成功页如果需要判断是否可跳转，应直接读取 fresh entitlements 的返回值或写入 React Query cache，不要只调用 `refresh()` 后立即跳转

## 注意事项

- 不要再把 `@insforge/nextjs` provider/hook 接回 `Providers.tsx`
- `AuthContext` 是前端唯一 auth 状态源
- `EntitlementsContext` 是前端所有付费功能开关的统一来源；不要在页面里重新按 `plan` 猜权限
- 刷新页面、打开新 tab、OAuth 回跳后的 session 恢复都应依赖本域 `app_access_token` / `app_refresh_token` cookies 和 `/api/auth/session`；不要回退到浏览器直连 Insforge refresh cookie
