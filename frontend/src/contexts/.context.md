# Contexts - React Context Providers

## 功能概述

全局状态通过 React Context 提供，挂载在 `components/Providers.tsx` 中。

当前认证体系走 server-cookie bridge：

- 登录/注册/邮箱验证通过 `frontend/src/app/actions/auth.ts` server actions 调 Insforge
- Session 恢复通过 `frontend/src/app/api/auth/session/route.ts`
- Token 存在本域 first-party httpOnly cookies：`app_access_token` / `app_refresh_token`
- `AuthContext` 成为唯一前端 auth 状态源
- 路由保护由项目自定义 `middleware.ts` 完成（只做 cookie gate；真正校验/刷新由 session route 完成）

## 文件

| 文件 | 职责 |
|------|------|
| `AuthContext.tsx` | 认证状态、登录/注册/验证邮箱/登出、登录后用户同步 |
| `SubscriptionContext.tsx` | 订阅状态与支付入口 |
| `EntitlementsContext.tsx` | 当前用户 entitlement 集合、`has(feature)` 判断、`refresh({ fresh })` 强刷 |

## AuthContext

### 提供的值

```typescript
{
  user: User | null,
  isLoading: boolean,
  isAuthenticated: boolean,
  setAuthenticatedUser: (user: User | null) => void,
  signIn(email, password): Promise<AuthActionResult>,
  signUp(email, password, name?, redirectPath?): Promise<SignUpResult>,
  signOut(): Promise<AuthActionResult>,
  signInWithGoogle(): Promise<AuthActionResult>,
  updateProfile({ name }): Promise<AuthActionResult>,
  resendVerificationEmail(email): Promise<AuthActionResult>,
  verifyEmail(otp, email?): Promise<AuthActionResult>,
  refreshUser(): Promise<void>,
}
```

### 状态来源

启动流程：

```text
mount
  -> AuthContext 调 /api/auth/session
  -> session route 校验 access token，必要时用 refresh token 换新 access token
  -> 返回 { user, accessToken }
  -> AuthContext setUser / setIsLoading(false)
```

不依赖：
- `useInsforge()`
- `sdk.isLoaded`
- `sdk.reloadAuth()`
- 浏览器直连 Insforge refresh cookie

### 登录

邮箱密码登录：
- `signIn()` → `signInAction()` server action
- server action 续写 first-party auth cookies，成功后 `setUser(result.user)`

Google OAuth：
- `signInWithGoogle()` → `startOAuthAction()`
- 浏览器跳转到 Google 授权页
- 回跳 `/auth/callback` → 服务端 exchange OAuth code → 续写 first-party cookies → 跳转目标页

### 注册与邮箱验证

- `signUp()` → `signUpAction()` server action
- 需要验证邮箱时返回 `requiresEmailVerification`，跳转 `/verify-email`
- `verifyEmail()` → `verifyEmailAction()` server action
- 验证成功后续写 cookies 并 `setUser(result.user)`

### 登出

1. `signOutAction()` 清本域 auth cookies
2. 清 `_cachedAccessToken`
3. 清 `AuthContext` user
4. `queryClient.clear()`

## SubscriptionContext

`SubscriptionContext` 没有因为本轮 auth 改造改变职责，仍然：

- 依赖 `AuthContext`
- 负责订阅状态、checkout、billing portal
- 通过 `getAccessToken()` 为付费接口补 Bearer token
- Stripe Checkout success_url 会带 `checkout=success&tier=...`，所以回跳页和
  `SubscriptionContext` 都能识别 checkout return；成功页负责最终等待
  `subscription-status?fresh=true` 与 `me/entitlements?fresh=true` 同时生效后再跳转
- Profile 订阅展示直接使用 API 返回的 `plan/status/access_expires_at` 计算，不使用
  `isPro/isMax`，因为后者会受 `NEXT_PUBLIC_ENABLE_PAYWALL=false` 影响；功能权限仍使用
  `EntitlementsContext`
- `SubscriptionContext` 透传支付 API 的 `cancel_at_period_end/cancel_at/canceled_at`
  为 `cancelAtPeriodEnd/cancelAt/canceledAt`。Profile 用这些字段展示“已取消但仍可用到期末”的状态；不要把 `status="active"` 直接等同于“仍会自动续费”。
- `status="active"` 和 Stripe `status="trialing"` 都代表 active access display；实际功能仍以
  `EntitlementsContext` / 后端 `has_entitlement()` 为准。

## EntitlementsContext

- 依赖 `AuthContext` 的登录状态
- 请求 `GET /api/payment/me/entitlements`
- 暴露 `has(feature)` 给 `PaywallGuard`、Profile 邮件偏好等前端 gate 使用
- `refresh({ fresh: true })` 会旁路后端 5 分钟订阅缓存；checkout 成功页如果需要判断是否可跳转，应直接读取 fresh entitlements 的返回值或写入 React Query cache，不要只调用 `refresh()` 后立即跳转

## 注意事项

- 不要再把 `@insforge/nextjs` provider/hook 接回 `Providers.tsx`
- `AuthContext` 是前端唯一 auth 状态源
- `EntitlementsContext` 是前端所有付费功能开关的统一来源；不要在页面里重新按 `plan` 猜权限
- `getAccessTokenSync()` / `getAccessTokenAsync()` 必须检查 JWT `exp`；缓存 token 已过期或 60 秒内过期时，sync 返回 `null`，async 通过 `/api/auth/session` 刷新，避免页面放久后付费/API入口带过期 Bearer token
