# Contexts - React Context Providers

## 功能概述

全局状态通过 React Context 提供，挂载在 `components/Providers.tsx` 中。

本轮认证回撤后：

- `Providers.tsx` 重新引入 `InsforgeBrowserProvider`
- `middleware.ts` 重新改回 `InsforgeMiddleware` 做首层受保护路由拦截
- `AuthContext` 回到“SDK user 为主，cookie recovery 为辅”的轻量模型
- 注册体验保留，但不再绑定到复杂恢复状态机

## 文件

| 文件 | 职责 |
|------|------|
| `AuthContext.tsx` | 认证状态、登录/注册/验证邮箱/登出 |
| `SubscriptionContext.tsx` | 订阅状态与支付入口 |

## AuthContext

### 提供的值

```typescript
{
  user: User | null,
  isLoading: boolean,
  isAuthenticated: boolean,
  signIn(email, password): Promise<AuthActionResult>,
  signUp(email, password, name?, redirectPath?): Promise<SignUpResult>,
  signOut(): Promise<AuthActionResult>,
  signInWithGoogle(): Promise<AuthActionResult>,
  updateProfile({ name }): Promise<AuthActionResult>,
  resendVerificationEmail(email): Promise<AuthActionResult>,
  verifyEmail(otp, email?): Promise<AuthActionResult>,
  refreshUser(): Promise<void>,
}
```

### 状态来源

`AuthContext` 本身不再维护一整套独立 auth 状态机。当前来源只有两层：

1. `useInsforge()` 提供的 SDK 状态
2. 当 SDK 当前没有 user 时，额外调用一次 `getAccessToken()` 触发统一兜底恢复

恢复流程：

```text
mount
  -> 等待 sdk.isLoaded
  -> 如果 sdk.user 已存在：结束
  -> 如果 sdk.user 不存在：调用 getAccessToken()
  -> getAccessToken() 内部才会在必要时 fallback 到 /api/auth/session
  -> token 恢复成功后：
       - 读取 sdk.getCurrentSession()
       - 先调用 sdk.reloadAuth()
       - 再用 sdk.setUser(...) 做兼容桥接
```

这就是当前唯一的补充恢复逻辑。页面层不再直接管理 cookie recovery 细节，也没有 tab visibility refresh、forced reauth、callback 手工 exchange 状态机。

### 登录

邮箱密码登录：

- `signIn()` 调 `lib/auth.ts` 的 `signIn()`
- 底层走 `POST /api/auth { action: 'login' }`
- 成功后优先调用 `sdk.reloadAuth()`
- 只有官方恢复失败时才 fallback 到 `sdk.setUser(...)`

Google OAuth：

- `signInWithGoogle()` 直接调用 `lib/auth.ts` 的 `signInWithGoogle()`
- 由 SDK/provider 默认链路处理跳转和恢复

### 注册与邮箱验证

这部分体验保留当前版本：

- `signUp()` 调 `sdk.signUp()`
- `emailRedirectTo` 指向 `/verify-email`
- `verifyEmail()` 调 `sdk.verifyEmail()`
- `resendVerificationEmail()` 调 `sdk.resendVerificationEmail()`
- 验证成功后再补写 profile name

也就是说，注册体验仍然是新的；只是登录恢复底座回到了旧版思路。

### 登出

当前登出流程：

1. `sdk.signOut()`
2. 清理 cached token / localStorage
3. 清 SDK auth header
4. `queryClient.clear()`

cookie 清理主逻辑在 `clearStaleAuthStateWithoutRedirect()` 与 `/api/auth DELETE` 那边。

## SubscriptionContext

`SubscriptionContext` 逻辑没有因为这次 auth 回撤发生结构变化，仍然：

- 依赖 `AuthContext`
- 负责订阅状态、checkout、billing portal
- 用 localStorage 做 5 分钟 TTL 缓存

## 注意事项

- `AuthContext` 现在依赖 `InsforgeBrowserProvider`，不要再把 provider 从 `Providers.tsx` 中拿掉
- 首层路由保护已经交给 `InsforgeMiddleware`，页面内 `router.push('/login')` 只作为兜底
- 登录页跳转依赖 `isAuthenticated`，不是依赖自定义 callback 完成标志
- `sdk.reloadAuth()` 现在是 Server Proxy 登录成功后的优先恢复手段，`sdk.setUser()` 只是兼容兜底
- `verifyEmail()` 目前优先走 SDK 默认链路；如果未来必须恢复 first-party cookie bridge，应尽量做成最小补丁，而不是重新引入多动作 auth 总线
