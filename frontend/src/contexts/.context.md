# Contexts - React Context Providers

## 功能概述

全局状态管理，通过 React Context 提供认证和订阅状态。挂载在 `components/Providers.tsx` 中。

## 文件

| 文件 | 职责 | 依赖 |
|------|------|------|
| `AuthContext.tsx` | 用户认证状态 (登录/登出/用户信息) | `@insforge/sdk`, `@/lib/auth`, Server Proxy |
| `SubscriptionContext.tsx` | 订阅状态 (isPro/plan/checkout) | `AuthContext`, `@/lib/auth` |

## AuthContext

### 提供的值

```typescript
{
  user: User | null,       // 当前用户
  isLoading: boolean,      // 初始化中 (localStorage 恢复 + Server Proxy refresh)
  isAuthenticated: boolean, // user !== null
  signIn(email, password): Promise<AuthActionResult>,
  signUp(email, password, name?, redirectPath?): Promise<SignUpResult>,
  resendVerificationEmail(email): Promise<AuthActionResult>,
  verifyEmail(otp, email?): Promise<AuthActionResult>,
  signOut(): Promise<AuthActionResult>,
  signInWithGoogle(): Promise<AuthActionResult>,
  completeOAuthCallback(code): Promise<AuthActionResult>,
  updateProfile({ name }): Promise<AuthActionResult>,
  refreshUser(): Promise<void>,
}
```

### Session 恢复流程 (useState + Server Proxy 模式)

```
mount -> AuthContext init effect
  1. restoreUserFromStorage()
     ├── localStorage 有 insforge-auth-token + insforge-auth-user
     │   ├── token 未过期 -> setUser(restored), setIsLoading(false), 结束
     │   └── token 已过期 -> 继续到步骤 2
     └── localStorage 无 token -> 继续到步骤 2
  2. Server Proxy refresh: POST /api/auth { action: 'refresh' }
     ├── 成功 -> syncClientAuthSession() + setUser() + setIsLoading(false)
     └── 失败 -> setIsLoading(false), user 保持 null (未登录)
```

AuthContext 通过 `useState` 管理用户状态，不依赖任何 SDK 内部状态管理。`@insforge/sdk` 只用于调用 auth API（signUp、signOut、resendVerificationEmail、setProfile、signInWithOAuth）；真正需要把 refresh token 桥接回应用域名的动作（邮箱验证、OAuth exchange）走 Server Proxy。

登录后的订阅同步、副作用逻辑已拆到 `components/AuthSubscriptionSync.tsx`，避免认证层混入业务 side effect。

### SDK 调用模式

所有 `@insforge/sdk` auth 方法返回 `{ data, error }` wrapper：
```typescript
const { data, error } = await insforge.auth.signUp({ email, password });
if (error) { /* handle */ }
if (needsEmailVerification(data)) { /* verification flow */ }
```

方法映射：
- `insforge.auth.signUp({ email, password, emailRedirectTo })` - 注册
- `insforge.auth.signOut()` - 登出 (SDK 端)
- `insforge.auth.setProfile({ name })` - 更新用户资料
- `insforge.auth.resendVerificationEmail({ email })` - 重发验证邮件
- `POST /api/auth { action: 'verify-email', otp, email? }` - 邮箱验证 + cookie bridge
- `insforge.auth.signInWithOAuth({ provider, redirectTo: '/auth/callback' })` - OAuth 发起
- `POST /api/auth { action: 'oauth-exchange', code, codeVerifier }` - OAuth code exchange + cookie bridge

### 登录流程

邮箱密码登录走 Server Proxy（`POST /api/auth { action: 'sign-in' }`），不走 SDK 直接登录。Server Proxy 从 Insforge Set-Cookie 头提取 refresh token 存在我们域名上。

Google OAuth 也不会直接回业务页，而是统一先回公开的 `/auth/callback`。原因是 callback 阶段还没有我们域名下的 auth cookie，如果直接回 `/for-you` 这类受保护页，会先被 middleware 重定向回 `/login`。

### 登出流程

1. `clearStaleAuthStateWithoutRedirect()` 统一清模块级 cached token / localStorage / SDK auth header
2. `insforge.auth.signOut()` (best-effort SDK 清理)
3. `DELETE /api/auth` (清 httpOnly cookies)
4. `setUser(null)` + `queryClient.clear()`

OAuth / callback 场景下，AuthContext 初始化完成后会调用 `cleanupAuthCallbackUrlParams()` 清理 URL 中残留的回调参数。

**关键**: 没有 `InsforgeBrowserProvider`、没有 `initialState`、没有 SSR auth seed。Session 恢复完全在客户端完成。

## SubscriptionContext

### 提供的值

```typescript
{
  isPro: boolean,              // 是否 Pro 用户
  isLoading: boolean,          // 订阅状态查询中
  plan: string,                // 'free' | 'pro'
  status: string,              // 'active' | 'trialing' | ...
  createCheckout(returnPath?),  // 发起支付
  openBillingPortal(),          // 打开账单管理
  refreshSubscription(),        // 刷新订阅状态
}
```

### PAYWALL_ENABLED 开关

`NEXT_PUBLIC_ENABLE_PAYWALL=true` 时才查询订阅 API，否则 `isPro=true` 跳过所有付费墙。

模块级常量，运行时不可改变。测试中无法通过 `vi.stubEnv()` 修改。

### 缓存

localStorage `sub_status` 缓存订阅状态，TTL 5 分钟，按 userId 隔离。

## 注意事项

- 两个 Context 都是 `'use client'`，只在客户端组件中可用
- 嵌套顺序: `AuthProvider` > `SubscriptionProvider` (订阅依赖认证)
- 在 Provider 外调用 `useAuth()` / `useSubscription()` 会抛错
- `signInWithGoogle()` 会优先使用 `sessionStorage.auth_redirect`，但 OAuth `redirectTo` 固定是 `/auth/callback`，最终业务跳转在 callback 页完成
- 登录/注册成功后的跳转现在由登录页监听 `isAuthenticated` 统一处理
- 注册后如果 SDK 返回 `requireEmailVerification=true`，登录页会跳到 `/verify-email`
- `AuthContext.signUp()` 现在会构造 `emailRedirectTo=/verify-email?redirect=...`，兼容邮件链接验证
- `AuthContext.resendVerificationEmail()` 会把 SDK 空返回归一成失败，避免 UI 误报"已发送"
- `AuthContext` 在 `/auth/callback?insforge_code=...` 场景会跳过 SDK 自动恢复，避免 SDK 先消耗 code 导致 Server Proxy 无法再桥接 refresh token
