# Edge Functions

Insforge Edge Functions live in this directory and are deployed with
`npx @insforge/cli functions deploy <slug> --file backend/app/edge_functions/<slug>.js`.

## mcp-auth

`mcp-auth.js` is the backend-facing Edge Function for TheMarketBrew MCP
browser/device authorization. Backend code in
`features/kol_research/mcp_auth.py` calls it with `X-Internal-Secret` when
`EDGE_FUNCTION_SECRET` is configured.

Actions:

- `start` creates a pending device authorization row.
- `authorize` binds a pending user code to the logged-in website user.
- `exchange` atomically consumes an authorized device code and stores a hashed
  MCP token.
- `verify` validates a hashed MCP token for account-gated MCP content/data
  endpoints.
- `revoke` marks the current MCP token revoked.
- `log_usage` records per-tool usage events.

Raw device codes and MCP bearer tokens are generated by the backend and are not
stored directly; the Edge Function persists hashes in
`mcp_device_authorizations` and `mcp_tokens`, plus audit rows in
`mcp_usage_events`.

## Cron Trigger

`cron-trigger.js` is the production schedule dispatcher used by Insforge
Schedules after the 2026-06-05 GitHub Actions cron migration.

- Function slug: `cron-trigger`
- Schedule URL: `https://9wmhxyi4.us-east.insforge.app/functions/cron-trigger`
- Auth: schedule requests must include `X-Internal-Secret: ${{secrets.EDGE_FUNCTION_SECRET}}`
- Backend auth: proxy forwards to Railway with `X-Cron-Secret` from Insforge `CRON_SECRET`
- Verification: call with `{"dry_run": true}` to validate registry/secrets/target URLs without forwarding to backend
- Payment grant cleanup schedule: `Cron - Payment Reconcile Expired Grants`
  (`bdd60d1a-0db1-4b28-ac99-9df97fe27e57`) runs daily at `10 8 * * *`
  UTC with body `{"job":"payment_reconcile_expired_grants"}`.

The proxy keeps the key failure checks that previously lived in GitHub
workflow shell scripts: daily report `sent=0`, personal digest `failed>2`,
weekly `broadcast_result`, KOL ingestion zero-stored tweets, and Twitter digest
broadcast `total>0 && sent=0`. It also exposes
`payment_reconcile_expired_grants`, which forwards to
`POST /api/payment/reconcile-expired-grants` for daily cleanup of expired
non-Stripe access grants, and `watchlist_monitor_paid_universe`, which forwards
to `POST /api/admin/watchlist-monitor/start-paid-universe` to start the paid For You
monitor ticker-universe background job. The monitor job intentionally returns
after the backend accepts the background task; full-universe generation can take
longer than the Edge Function HTTP gateway timeout, so completion/failure
details are checked in Railway logs or by manually retrying the synchronous
`generate-paid-universe` endpoint for missing tickers. The `onboarding_drip` job is now a legacy no-op:
it may still be scheduled, but the backend endpoint returns `disabled=true` and
sends no email. The proxy validates against the full backend response but
returns only `body_summary` fields to avoid writing full report content into
schedule logs.

Current migrated jobs and schedule IDs are tracked in
`docs/plans/completed/cron-migration-gha-to-insforge.md`.

## subscriptions

`subscriptions.js` is the backend-facing Edge Function for the single
`subscriptions` table. Payment code uses it for `get`, `get_by_customer`,
`upsert`, `set_lifetime`, `list_entitled`, and
`list_expired_access_grants`.

`set_lifetime(true)` writes Max plan/status and caller-provided Max
entitlements. `set_lifetime(false)` only flips `is_lifetime=false`; normal
read-time entitlement rules and Stripe/webhook state then decide the user's
effective tier. If a hard downgrade is required during revocation, update the
Edge Function and tests together to clear plan/status/access fields explicitly.

`list_expired_access_grants` returns rows whose `access_expires_at <= now` and
`is_lifetime` is not true. The backend payment reconciliation endpoint then
updates those rows to `plan="free"`, `status="expired"`, `entitlements=[]`,
and syncs Resend segments. Read-time entitlement checks still enforce expiry;
the cron path is for data/display/segment cleanup.

Payment sync also writes the actual Stripe subscription Price into
`stripe_price_id`, `billing_amount_cents`, `billing_currency`,
`billing_interval`, and `billing_interval_count` (migration:
`backend/migrations/subscription_billing_price.sql`). These fields are used by
Profile to show early-bird/historical renewal prices instead of public plan
copy.

Stripe account migration fields live on the same row:
`stripe_account_ref`, `legacy_stripe_customer_id`,
`legacy_stripe_subscription_id`, `stripe_migration_state`, and
`stripe_migrated_at`. The `subscriptions?action=list_all` response includes
these fields so backend reconciliation scripts can map old-account Stripe
subscriptions to new-account subscriptions without direct table reads. The
Stripe account migration preflight/export/reconcile scripts all depend on
`list_all` as their local subscription inventory source.

## community-access

`community-access.js` is the backend-facing Edge Function for partner/community
Agent grants. MVP stores Panda Agent access in `community_access_grants` by
normalized email, independent of Stripe subscriptions.

Actions:

- `get_by_email` reads one grant by `(partner_id, email_normalized)`.
- `list` returns recent grants, with optional status and email substring filter.
- `bulk_upsert` creates/reactivates active grants from an admin-provided email list.
- `mark_seen` records the logged-in user id that matched a grant.
- `revoke` marks a grant revoked.

No public caller should access this function directly; FastAPI performs user or
admin auth before calling it.

## vector-store

`vector-store.js` is the backend-facing Edge Function for generic vector
documents/chunks. Backend code calls it with `X-Internal-Secret` for writes and
searches. Keep `vector-store.js` and `vector-store.sql` in sync:

- `search` calls the pgvector RPC `match_vector_chunks` for semantic retrieval.
- `search_text` calls `search_vector_chunks_text` for exact title/content/
  metadata keyword retrieval using the same source/user/metadata filters.

KOL hybrid retrieval uses both actions: exact text/metadata lanes catch explicit
symbols and names, while the vector lane handles fuzzy or adjacent concepts.

## watchlist-monitor

`watchlist-monitor.js` is the backend-facing Edge Function for the V0 AI
watchlist monitor. Backend code calls it with `X-Internal-Secret`; user JWTs are
verified by FastAPI before this function is invoked.

Actions:

- `upsert_brief` upserts one shared ticker daily brief into
  `ticker_daily_briefs` on `(symbol, brief_date, model_version)`.
- `latest_briefs` returns the latest available brief per requested symbol.

Production InsForge migrations live in `migrations/`, starting with
`20260617193000_watchlist-monitor-v0-schema.sql`. A module-local schema
reference also lives at `backend/migrations/watchlist_monitor_v0_schema.sql`. Keep the
Edge Function action names in sync with `features/watchlist_monitor/db.py`.
Brief rows include `news_summary` alongside `headline` and `ai_take`, plus
`technical_monitor` JSON for the monitor page's technical summary, key levels, and
deterministic technical signals, plus `event_candidates` JSON for future
company/event monitoring. Keep these columns in the migration, Edge Function
payload, and Pydantic models together.
