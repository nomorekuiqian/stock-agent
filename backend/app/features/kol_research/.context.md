# features/kol_research — 博主投研 Agent

## Purpose

ADK LlmAgent that combines `shared/kol_persona` (loads persona lenses
as ADK Skills) with `shared.data_tools.research_tools` (market data) and
`search_kol_tweets` (RAG over `vector_chunks` filtered to KOL tweets).

Companion to `features/screener.research_agent` (neutral /research):
- Neutral agent: friendly stock guide for beginners, full screener tools
- KOL agent: thinks with the selected persona's methodology, omits screener selection tools

Both share `/research` UI; PersonaSelector decides which endpoint to hit.

## Files

- `agent.py` — singleton LlmAgent per persona; `answer_kol_research` /
  `stream_kol_research` public entry points. The prompt explicitly separates
  static distilled skill coverage from indexed tweet RAG: `search_kol_tweets`
  reads already-ingested `kol_tweets/vector_chunks`, not live Twitter/X, and a
  newer RAG hit can supersede an older "not covered as of <cutoff>" skill note.
  The shared KOL prompt treats framework / sector / ticker lenses as optional:
  thin RAG-only personas such as `pandacircle` should answer from core prompt +
  query-planned hybrid RAG + current data instead of explaining that no static
  lens exists. For specific stocks / sectors / events, the prompt asks the
  model to pass ticker/company/product/event aliases via
  `search_kol_tweets(..., query_variants=[...])`; the retrieval tool then runs
  exact text, ticker metadata, and vector semantic lanes.
- `input_guard.py` — deterministic ticker / URL / macro-news intent parsing,
  obvious data prefetch, and post-run data coverage warnings
- `router.py` — `/api/kol_research/*` endpoints. Chat + conversations
  previously sat behind the `kol_research_agent` user flag; the gate has been
  rolled out (any authenticated user can call them). `require_kol_research_flag`
  is kept as a no-op token-only dependency so endpoints don't need to be
  re-wired for rollback — uncomment the `FLAG_KEY in flags` check in
  `require_kol_research_flag` to re-gate. The **Cockpit read endpoints are
  PUBLIC** (see below). The Market Lens MCP content endpoints require an MCP
  account token issued through the device/browser authorization flow.
- `models.py` — Request/response DTOs (markdown output + LLM follow-up `options` + `kol_chunks` + `activated_skills` + `tool_calls`)
- `mcp_auth.py` — TheMarketBrew MCP device authorization, opaque MCP token
  verification, revoke, and usage logging helpers. Raw MCP tokens and device
  codes are never stored directly; only hashes are sent to the edge function.
- `mcp_data.py` — account-gated P0 MCP data plane. It wraps
  `shared.data_tools` brief, stock, macro, report, news, calendar, and
  transcript helpers into section-level envelopes for MCP clients.
- `cockpit.py` — read-only aggregation for the public `/kol/{username}` page
  (NOT the chat). Ticker extraction from raw `kol_tweets.text` via a curated
  Chinese-name → ticker dictionary (`TICKER_ALIASES`); qinbafrank uses no
  `$cashtag`, so regex/cashtag alone won't work and no LLM enrichment is used.
  Also holds curated legacy cockpit display config. TTL-cached tweet index is
  fetched via the public `kol-tweets` GET `list` action, paginated.
- `cockpit_v3.py` — persona-neutral cockpit summaries backed by promoted
  methodology material roots; used by non-legacy persona context packs.
- `skill_cockpit.py` — qinbafrank legacy skill/cockpit adapter used by the
  public page and Frank MCP tools while v3 material is promoted.

Except for `mcp/status` and the public device start/token polling endpoints,
MCP content/data endpoints require `Authorization: Bearer <mcp_token>` and
return `401 {"detail": {"code": "auth_required", "login_tool":
"market_lens_login", ...}}` when the adapter has not been authorized. The
website approval route uses normal `verify_user_token`, so the user must have a
TheMarketBrew account and active web session before approving a device code.
MCP auth data is persisted through the `mcp-auth` edge function and the
`mcp_device_authorizations`, `mcp_tokens`, and `mcp_usage_events` tables.

`mcp_materials.py` is the filesystem-backed distilled material index. It
resolves each persona to one independent material root, then scans
`core|framework|macro|sector|ticker` under that root and returns
persona-neutral lens metadata. Direct formal roots such as
`features/twitter/methodologies/qinbafrank` and
`features/twitter/methodologies/aleabitoreddit` are supported. Registered
persona skill dirs are also supported for future experimental bundles, but
promoted personas should live beside `qinbafrank` under `methodologies/`.
Keep persona roots isolated: never fall back from one persona's missing lens to
another persona's material.

`mcp/lenses` returns an index only: lens type/id, description, coverage,
relative path, line count, and Evidence Map id count. `mcp/lenses/{type}/{id}`
returns the full distilled markdown body, parsed sections, metadata, Evidence
Map tweet IDs, and per-lens call guidance. `mcp/lenses/search` performs a
simple lexical search across all distilled markdown material and is intended
for routing broad user questions to exact lens IDs. `mcp/evidence/by-ids`
bridges Evidence Map tweet IDs back to original tweet text through the cockpit
reader.

`mcp/evidence/by-ids` first asks the live cockpit reader for original tweets.
Formal persona material roots should not ship local `evidence/` directories.
If an experimental bundle still has a local `evidence/all-tweets.jsonl`, the
read-only fallback remains scoped to that selected persona's material root.

`mcp/search` calls `features.vector.service.search` with `source_type=kol_tweet`
and `metadata.author_username={u}`, then converts chunks through
`chunk_to_persona_result` so the returned evidence shape matches KOL chat
citations. This is an indexed vector search over the latest embedded corpus,
not a live Twitter/X fetch; user-facing answers should call it indexed or
vector corpus evidence.

`mcp/data/catalog` tells the adapter which P0 data tools and section names are
available. `mcp/data/brief` is the default coarse-grained data entry point:
stock, peer, macro, and industry briefs. `mcp/data/stock` returns requested
fine-grained stock sections such as quote, profile, fundamentals, valuation,
technical, news, calendar, price history, transcript, insider trading, press
releases, and broad market overview. `mcp/data/market` returns market,
macro/liquidity/risk/sentiment, economic/earnings calendar, morning report,
weekly report, and Twitter digest sections. `mcp/data/news` returns
source-attributed recent stock, market, press release, morning report, and
Twitter digest news. Each response is an envelope with `ok`, `tool`, `request`,
`data`, `errors`, `auth`, `freshness`, and `limits`; section-level failures
are returned in `errors` instead of fabricated success text.

`mcp/market-brief` is a legacy compatibility bridge and reuses
`shared.data_tools.briefs`:
`get_stock_brief`, `get_peer_brief`, `get_industry_brief`, and
`get_macro_brief`. Stock / peer / industry briefs primarily depend on FMP;
macro brief reads the macro cache populated by the existing FRED/FMP data
pipeline.

`mcp/context` and `mcp/workflow` include backend-only `methodology_context` and
P0 data-plane fields. For every persona, methodology context includes
`selected_lenses`: core + macro, one workflow-appropriate framework lens, exact
ticker lenses, and sector lenses inferred from explicit sector input, ticker
metadata, or question search. Frank can still include legacy `skill_cockpit`
summaries, but non-Frank personas must use their own selected material lenses
and `cockpit_v3` summaries. `mcp/workflow` supports `stock_diagnosis`,
`market_regime`, `compare`, and `research_memo`. It returns a context pack for
the user's own Agent to write the final answer; it does not call the website
chat endpoint and does not return final investment advice. The context pack
includes `kol_chunks`, legacy `market_context`, structured `data_context`,
`news_context`, `data_freshness`, `data_errors`, `methodology_context`,
`answer_discipline`, and `suggested_answer_shape`.

For non-Frank v3 persona sector pages, `cockpit_v3` returns representative
tweet ids from the Evidence Map. `router.py` resolves those ids through the
persona cockpit index before returning `rep_tweets`, so frontend sector panels
can show the "past comments" column without re-implementing evidence lookup.
Ticker timelines also support v3 personas: the endpoint first reuses the live
cockpit ticker timeline, then falls back to raw text matches, then to promoted
ticker summary nodes. Keep the default limit small (10) for the stock detail UI.

`POST /api/kol_research/chat` and `/chat/stream` remain authenticated for the
website chat flow and are not exposed through the MCP adapter in P0.
All persona chat calls share the general research quota via
`features.quota.service.consume_quota()`. Free / Pro users get the same daily
quota as neutral `/research`; Max users are unlimited through
`ai_research_engine`. Qinbafrank no longer has a separate `kol_pack_qinbafrank`
gate or lifetime trial bucket. The mounted FastMCP remote endpoint under
`/frank/mcp/` remains available for experimentation but is not the primary
distribution path.

Enrichment surfacing: `_slim_tweet` now exposes `content_type`, `key_claim`,
`topics`, `ticker_stances`, and reference provenance fields
(`source_author_username`, `source_kind`, `article_title`) from `symbols` JSONB
onto every feed row so the cockpit UI can filter, label, and attribute source
articles without re-reading raw enrichment. `topics` is derived
deterministically by `_classify_tweet_topics` from `(content_type, sectors)`;
the topic tree and feed share `_default_feed_visible` for the low-quality-reply
filter so tree counts always match feed hit counts.

`feed.total` is the visible feed count after default low-quality-reply
filtering and any query filters. `feed.raw_total` is the full ingested tweet
count from the cached cockpit index before that visibility filter; use
`raw_total` for page chrome / KPI labels that say "入库推文".

Ticker opinion timelines are dynamic reads, not static curated arrays. A new
Frank tweet appears in a ticker timeline after it has been ingested into
`kol_tweets`, matched by `TICKER_ALIASES`, and the cockpit cache has refreshed
or rebuilt. Enriched `key_claim` / `content_type` still improve labeling, but
they are not required for inclusion: if a tweet intersects the ticker and is
not explicit `noise`, the timeline falls back to a short original-text excerpt.
The endpoint returns newest-first so the UI starts from the most recent view
and walks back toward the original thesis.

`feed` also supports `tickers=` and `keywords=` comma-separated OR filters in
addition to the legacy `ticker`, `sector`, and `topic` filters. The read limit
is capped at 1500 for product timelines. Qinbafrank sector pages use these
broader filters to build dynamic board timelines from actual tweet
intersections, so RWA / political-stock / prediction-market content is not
limited to the older static curated `sourceId` lists.

These are intentionally **not** flag-gated (the cockpit page is public; chat
requires login, and Qinbafrank chat additionally checks the Ultra pack gate).
FMP failures degrade gracefully. Legacy sector keys: `ai-compute-base` / `ai-hbm` / `ai-datacenter` / `ai-power` /
`ai-application` / `crypto` / `macro`.

Product-facing sector keys: `ai-infrastructure`, `crypto-stablecoin-rwa`,
`defense-and-space`, `software-ai-disruption`, plus `macro-regime` for the
standalone Macro page. The raw skill corpus also has subtopic files
`power-and-physical-ai`, `semiconductor-memory-hbm`, and `fintech-brokerage`;
these are hidden from the sector nav and rolled into the top-level AI 基建 /
加密金融 boards for counts, tickers, and representative evidence.

`kol_tweets.symbols` does contain enrichment metadata (ticker stances, sector
tags, quality/content_type depending on enrichment shape), but the Sector
Atlas should not treat those raw sector tags as product navigation. The skill
Atlas is driven by distilled methodology files; DB enrichment is supporting
metadata for digest/search/backfill and can be mapped into the 4 boards when
building future live filters.

`tweets/by-ids` reads from the same TTL-cached cockpit index and preserves the
requested id order. It powers the Frank industry-map / highlights long-form
reader, so it should return the original tweet or X article text without
additional summarization or LLM rewriting. If a requested evidence id is missing
from cache, or the cached body is only a bare URL (common for X Articles), the
endpoint forces one index rebuild before returning. The endpoint caps requests
at 30 ids to prevent accidental full-feed reads.

## Answer framework

`agent.py` uses a short, persona-neutral outer prompt. Its role definition is
"KOL methodology investment analyst": help users understand stocks, sectors,
market themes, or news through the selected persona's historical public views,
long-term methodology, and current market/company data. The outer prompt does
not define persona-specific voice, answer templates, or decision frameworks;
those belong in the selected persona's skill files.

There is no global response-mode table. The default answer stance is deep
research: clear conclusion, enough evidence, and complete explanation. Only
explicit user requests such as `简单说 / 两句话 / 只选一个 / 只要结论` should
make the answer short.

The outer prompt only defines shared orchestration:
- classify the user request as stock, sector, macro, news, methodology,
  comparison, opportunity discovery, or historical-view follow-up;
- treat `core` and `macro` as always-on context;
- load the most relevant framework skill, using `list_skills` if uncertain;
- load methodology-related framework skills when the user asks "why / how to
  judge / framework / method / how to understand", or when there is no recent
  direct persona view and the answer needs the persona's long-term thinking;
- load ticker skills for stock-specific questions and sector skills for
  industry/theme questions;
- retrieve indexed tweet evidence with `search_kol_tweets`;
- call stock / peer / industry / macro brief tools for current-data judgments;
- separate historical views, current data, methodology interpretation, and
  future changes to watch.

Historical-view citations must mention approximate time or original context and
use only the current turn's `[#N]` evidence from `search_kol_tweets`. If static
skill coverage says a ticker was not covered as of a corpus cutoff, but current
indexed tweet RAG returns later direct hits, the answer should state both facts
with exact dates and use the later RAG evidence. If there is no direct coverage,
say so before making a bounded methodology/data-based interpretation.

The skill files split responsibilities:
- `framework/ask-about-*.md` — intent-level rules: what the user is really
  asking, what the active persona would check first, required tools, answer
  shape, terminology, and route exits.
- `macro/`, `sector/`, `ticker/` playbooks — knowledge packs: active persona
  historical logic, key variables, plain-language explanations, support /
  weakening signals, future changes to watch, and evidence map.
- `search_kol_tweets` — only source for user-visible `[#N]` citations.

Keep shared safety/citation/tool-order rules in `agent.py`; keep persona voice,
domain variables, and decision matrices inside the relevant skill. Framework
skills must not rely on a mandatory global answer template.

`input_guard.py` sits before the LLM. It resolves explicit tickers and page
context such as "this stock", injects pre-fetched `get_stock_brief` /
`get_macro_brief` data for obvious requests, and appends a downgrade warning if
the turn did not cover required data. The `/research` frontend sends the current
Research Desk context as `content_context` when available; for stock panels it
at least sends `{ type: "stock", symbol }` so short KOL follow-ups can resolve
the ticker. This context is only for answer grounding. KOL mode still uses the
right panel for historical tweet evidence (`KolChunksPanel`) rather than agent
navigation.

Eval coverage for this answer framework lives in
`backend/evals/kol_research/`. The deterministic evaluator checks tool
coverage, citation validity, forbidden advice language, optional max/min
length, forbidden sections for concise prompts, and jargon translation. Do not
make four-section headings a global hard invariant again; add case-specific
shape checks instead.

Final answers pass through a small output sanitizer in `agent.py`: it translates
raw internal labels such as `coverage: high` into normal Chinese, fixes adjacent
citations, and removes code formatting from ordinary product / metric words
while keeping real tickers and numeric thresholds. It also caps bold emphasis
and downgrades common trading-action phrases like "分批建仓" into conditional
"分批评估" language. The sanitizer also downgrades over-strong KOL answer
phrases such as "非常值得关注", "黄金期", and "国王制造者" into calmer wording
so the final text does not sound like direct trading advice.

KOL follow-up chips are generated server-side after the final answer. The main
KOL answer still streams normally; before the final SSE payload, `agent.py`
runs a small structured `kol_follow_up_options` LLM pass on the user question,
assistant answer, active content context, and slim `kol_chunks`. The result is
returned as `KolResearchResponse.options`. Generation is best-effort: timeout,
schema, or model failures return `[]`, and the frontend falls back to its local
deterministic chips. The generator must avoid direct buy/sell, position, target
price, or short-term trading questions.

Unary `_run_session` uses ADK SSE streaming. If ADK emits only tool calls and no
user-visible final text, the run loop asks once more in the same ADK session for
a final answer based on the already-loaded skill/tool context. If ADK emits only
partial text without a final aggregate, the partial text is used as the fallback
response body. This prevents empty chat responses after successful skill loads.

## Run-loop contextvars

The streaming entry point sets these before invoking the agent so callbacks
can plumb data into the response payload + SSE events:

- `persona_chunks_buffer` (from `shared.kol_persona.tools`) — chunks the LLM retrieved
- `_activated_skills` — lens skill names the LLM loaded via `load_skill` tool
- `_tool_call_log` — every tool call (excluding `set_model_response`) with duration
- `_navigate_buffer` — candidate right-panel navigations derived from tool args
- `_sse_queue` — emits `skill_activated` / `tool_call_start` / `tool_call_end` events
- `_tool_started_at` — monotonic timestamps for duration measurement

SSE `error` events include a short `code` when possible:
`context_too_long`, `model_schema_error`, `agent_timeout`, `agent_setup_error`,
or `agent_error`.
The frontend maps these to user-safe messages instead of showing raw exceptions.

Tool calls are capped per turn for latency control. `google_search` is limited
to 1 call, and `search_kol_tweets` is limited to 3 calls; extra KOL RAG calls
return a structured `rate_limited` payload and the agent must answer from the
evidence / skills / data already gathered.

## Debugging KOL chat failures

The frontend now separates backend error codes, HTTP errors, client timeout,
network failure, and "stream closed without final". Diagnose by walking these
four checkpoints in order — the first one that **does NOT** show a matching
line is where the failure happened.

| # | Where | What to look for | Tool |
|---|---|---|---|
| 1 | Browser **Network** tab | `POST /api/kol_research/chat/stream` exists, returns `200`, body is SSE | DevTools |
| 2 | Browser **Console** | `[KOL Research] backend error event:` (backend sent error) or `[KOL Research] no final event` (stream closed cleanly without answer) — both include the raw payload | DevTools |
| 3 | Backend access log | `POST /api/kol_research/chat/stream 200 NNNms` shows the request reached the route | `tail -f /tmp/uvicorn-frank.log` |
| 4 | Agent log | `kol chat request: persona=X message=...` confirms the agent generator started. Failure path also logs `kol chat failed: persona=X elapsed=Ys code=Z err=...` with full stack via `logger.exception` | same log |

**Reading the failure modes**:

- **Checkpoint 1 missing** → frontend never sent the request. Common causes: new
  KOL URL effect signature ref skipped, persona/agent state mismatch, click
  handler bug. Inspect the URL effect in `frontend/.../research/page.tsx`.
- **Checkpoint 2 has `[KOL Research] no final event`** → backend opened SSE
  then closed cleanly. Most common: `StatReload` mid-stream (dev only), proxy
  timeout, or quota dispatch returned without yielding `final`.
- **Checkpoint 3 missing** → request was rejected by middleware before route
  dispatch. Check feature flag (`kol_research_agent`), auth dep, CORS preflight.
- **Checkpoint 4 has `kol chat request:` but no `final` event and no failure
  log** → agent ran but yielded no `final`. Check `stream_kol_research` for an
  early `return` path that skipped `final`. The success path is `yield {"type":
  "final", "data": ...}` at the end.
- **Checkpoint 4 has `kol chat failed:`** → `logger.exception` includes the
  stack trace. Read the stack to identify which tool / skill / model call blew
  up. Code field (`context_too_long` / `model_schema_error` / `agent_error`)
  is a coarse hint.

## Persistence

Reuses `picker-conversations` Insforge edge function (same table as neutral
`/research`). KOL-specific metadata lives inside the JSONB `data` field:

```json
{
  "agent_kind": "kol_research",
  "persona_username": "qinbafrank",
  ...
}
```

Frontend filters list by `data.agent_kind`. **No DB migration was required.**

Chat runs now also pass through `features/agent_runtime` before invoking ADK:

- `AgentRunRequest` carries `agent_id`, `user_id`, `conversation_id`, message,
  content context, and fallback request history.
- `PickerConversationSessionStore` can read `picker_conversations.data.messages`
  when both `user_id` and `conversation_id` are available; otherwise it falls
  back to request `history`.
- `DefaultContextEngine` owns prompt assembly and history budget trimming.
- Runtime writes go to the new additive-only `agent_session_events` store
  when `agent-sessions` is deployed, plus in-memory fallback. It still does not
  write `picker_conversations`; the frontend owns that existing row format.
- Runtime session metadata writes `agent_kind=kol_research` and
  `persona_username`, so `agent_sessions` can identify this as a KOL session
  without scanning event payloads.
- For first-turn KOL conversations, the frontend preallocates a UUID, sends it
  as `conversation_id`, then creates the `picker_conversations` row with the
  same id after the final response. This lets the first turn write to
  `agent_sessions` / `agent_session_events` immediately.
- Runtime event coverage now includes `context_snapshot`, `tool_call_completed`,
  `error`, and `ui_navigation` in addition to user/assistant messages. The
  frontend includes `active_content` / `content_stack` in KOL conversation saves
  so right-panel restore state can live in `agent_sessions.metadata.ui_state`.

## Access gating

Chat + conversation routes use `require_kol_research_flag`, but the function is
currently a token-only dependency kept for rollback compatibility. It no longer
checks the `kol_research_agent` feature flag. The **Cockpit read endpoints are
NOT gated** — `/kol/{username}` is publicly browsable.

`_consume_kol_chat_access()` delegates directly to the shared quota service for
every persona, including Qinbafrank. When quota is exhausted, unary chat returns
HTTP 429 and SSE returns an `error` event whose message points users to Max.

**Per-persona flag gating** (`_FLAG_GATED_PERSONAS` in `router.py`): a persona
can be hidden behind a feature flag. `GET /personas` drops gated personas the
caller lacks the flag for, and `/chat` + `/chat/stream` call
`_ensure_persona_allowed` (→ 403) before consuming quota. Currently
`pandacircle` → `pandacircle_persona` flag, scoped via `FlagDef.emails` allowlist
to specific tester accounts (see `features/flags/registry.py`). Flag read failure
fails closed (persona hidden). To roll out wider, broaden the flag's `emails=`
(or set `admin_default=True` / grant DB rows), or remove the persona from
`_FLAG_GATED_PERSONAS` for everyone.
