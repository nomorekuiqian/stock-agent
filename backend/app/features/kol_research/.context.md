# features/kol_research — 博主投研 Agent

## Purpose

ADK LlmAgent that combines `shared/kol_persona` (loads qinbafrank lenses
as ADK Skills) with `shared.data_tools.research_tools` (market data) and
`search_kol_tweets` (RAG over `vector_chunks` filtered to KOL tweets).

Companion to `features/screener.research_agent` (neutral /research):
- Neutral agent: friendly stock guide for beginners, full screener tools
- KOL agent: thinks with qinbafrank's methodology, omits screener selection tools

Both share `/research` UI; PersonaSelector decides which endpoint to hit.

## Files

- `agent.py` — singleton LlmAgent per persona; `answer_kol_research` /
  `stream_kol_research` public entry points
- `input_guard.py` — deterministic ticker / URL / macro-news intent parsing,
  obvious data prefetch, and post-run data coverage warnings
- `router.py` — `/api/kol_research/*` endpoints. Chat + conversations are
  flag-gated; the **Cockpit read endpoints are PUBLIC** (see below)
- `models.py` — Request/response DTOs (markdown output + `kol_chunks` + `activated_skills` + `tool_calls`)
- `cockpit.py` — read-only aggregation for the public `/kol/{username}` page
  (NOT the chat). Ticker extraction from raw `kol_tweets.text` via a curated
  Chinese-name → ticker dictionary (`TICKER_ALIASES`); qinbafrank uses no
  `$cashtag`, so regex/cashtag alone won't work and no LLM enrichment is used.
  Also holds curated legacy cockpit display config. TTL-cached tweet index is
  fetched via the public `kol-tweets` GET `list` action, paginated.

## Cockpit endpoints (PUBLIC — page browses without login)

```
GET /api/kol_research/personas/{u}/profile             methodology core + sector card fronts
GET /api/kol_research/personas/{u}/sectors             skill sector atlas list
GET /api/kol_research/personas/{u}/sectors/{key}       skill sector detail: rules + evidence + tickers + rep tweets
GET /api/kol_research/personas/{u}/industry_chain/{key} skill industry chain for AI / crypto / defense
GET /api/kol_research/personas/{u}/tickers             ticker list + mention counts + current price (FMP)
GET /api/kol_research/personas/{u}/tickers/{ticker}    verbatim tweets + FMP price series + fundamentals
```

These are intentionally **not** flag-gated (the cockpit page is public; only
chat requires `kol_research_agent`). FMP failures degrade gracefully. Legacy
sector keys: `ai-compute-base` / `ai-hbm` / `ai-datacenter` / `ai-power` /
`ai-application` / `crypto` / `macro`.

Product-facing sector keys: `ai-infrastructure`, `crypto-stablecoin-rwa`,
`defense-and-space`, `software-ai-disruption`, plus `macro-regime` for the
standalone Macro page. The raw skill corpus also has subtopic files
`power-and-physical-ai`, `semiconductor-memory-hbm`, and `fintech-brokerage`;
these are hidden from the sector nav and rolled into the top-level AI 基建 /
加密金融 boards for counts, tickers, and representative evidence.

`kol_tweets.symbols` does contain enrichment metadata (ticker stances, sector
tags, quality/content_type depending on enrichment shape), but the Sector
Atlas should not treat those raw sector tags as product navigation. The skill
Atlas is driven by distilled methodology files; DB enrichment is supporting
metadata for digest/search/backfill and can be mapped into the 4 boards when
building future live filters.

## Tool roster

```
[
  SkillToolset(skills=framework / sector / ticker playbooks),
  search_kol_tweets,                       # KOL RAG
  *brief_tools,                            # get_stock_brief / get_peer_brief / get_macro_brief / get_industry_brief
  get_technical_analysis,                  # rare technical escape hatch
  get_report_by_date, list_recent_reports, # daily reports
  GoogleSearchTool,                        # fallback
]
```

**Intentionally excluded** from the neutral set:
- `execute_screener` / `filter_by_tickers` / `get_field_distribution` / `list_available_sectors`
  — universe-wide selection doesn't fit qinbafrank's "follow the industry chain" approach.

## Answer framework

`agent.py` keeps only the cross-framework answer contract: non-factual answers
must close `one-line conclusion -> causal chain -> scenario tree -> retail
implication -> falsification condition`. This is the product quality bar, not a
domain-specific method.

For simple retail questions such as "怎么看 X", "能买吗", "要卖吗", or
"这个新闻是利好还是利空", the agent should use the short version of that
contract: direct conditional answer first, then one causal chain, 2-3 signals,
and a retail implication. Do not turn these questions into long research notes
unless the user asks for depth.

The skill files split responsibilities:
- `framework/ask-about-*.md` — intent-level rules: what a good answer for this
  question type must include.
- `macro/`, `sector/`, `ticker/` playbooks — knowledge packs: qinbafrank's
  historical logic, thresholds, cases, and evidence map.
- `search_kol_tweets` — only source for user-visible `[#N]` citations.

Keep safety, citation, and output-format rules in `agent.py`; do not duplicate
them inside every skill. Keep domain variables and decision matrices inside the
relevant skill.

`input_guard.py` sits before the LLM. It resolves explicit tickers and page
context such as "this stock", injects pre-fetched `get_stock_brief` /
`get_macro_brief` data for obvious requests, and appends a downgrade warning if
the turn did not cover required data. This improves reliability for short retail
questions without relying on prompt compliance alone.

Final answers pass through a small output sanitizer in `agent.py`: it translates
raw internal labels such as `coverage: high` into normal Chinese, fixes adjacent
citations, and removes code formatting from ordinary product / metric words
while keeping real tickers and numeric thresholds. It also caps bold emphasis
and downgrades common trading-action phrases like "分批建仓" into conditional
"分批评估" language.

## Run-loop contextvars

The streaming entry point sets these before invoking the agent so callbacks
can plumb data into the response payload + SSE events:

- `persona_chunks_buffer` (from `shared.kol_persona.tools`) — chunks the LLM retrieved
- `_activated_skills` — lens skill names the LLM loaded via `load_skill` tool
- `_tool_call_log` — every tool call (excluding `set_model_response`) with duration
- `_navigate_buffer` — candidate right-panel navigations derived from tool args
- `_sse_queue` — emits `skill_activated` / `tool_call_start` / `tool_call_end` events
- `_tool_started_at` — monotonic timestamps for duration measurement

SSE `error` events include a short `code` when possible:
`context_too_long`, `model_schema_error`, `agent_timeout`, `agent_setup_error`,
or `agent_error`.
The frontend maps these to user-safe messages instead of showing raw exceptions.

Tool calls are capped per turn for latency control. `google_search` is limited
to 1 call, and `search_kol_tweets` is limited to 3 calls; extra KOL RAG calls
return a structured `rate_limited` payload and the agent must answer from the
evidence / skills / data already gathered.

## Debugging KOL chat failures

The frontend now separates backend error codes, HTTP errors, client timeout,
network failure, and "stream closed without final". Diagnose by walking these
four checkpoints in order — the first one that **does NOT** show a matching
line is where the failure happened.

| # | Where | What to look for | Tool |
|---|---|---|---|
| 1 | Browser **Network** tab | `POST /api/kol_research/chat/stream` exists, returns `200`, body is SSE | DevTools |
| 2 | Browser **Console** | `[KOL Research] backend error event:` (backend sent error) or `[KOL Research] no final event` (stream closed cleanly without answer) — both include the raw payload | DevTools |
| 3 | Backend access log | `POST /api/kol_research/chat/stream 200 NNNms` shows the request reached the route | `tail -f /tmp/uvicorn-frank.log` |
| 4 | Agent log | `kol chat request: persona=X message=...` confirms the agent generator started. Failure path also logs `kol chat failed: persona=X elapsed=Ys code=Z err=...` with full stack via `logger.exception` | same log |

**Reading the failure modes**:

- **Checkpoint 1 missing** → frontend never sent the request. Common causes: new
  KOL URL effect signature ref skipped, persona/agent state mismatch, click
  handler bug. Inspect the URL effect in `frontend/.../research/page.tsx`.
- **Checkpoint 2 has `[KOL Research] no final event`** → backend opened SSE
  then closed cleanly. Most common: `StatReload` mid-stream (dev only), proxy
  timeout, or quota dispatch returned without yielding `final`.
- **Checkpoint 3 missing** → request was rejected by middleware before route
  dispatch. Check feature flag (`kol_research_agent`), auth dep, CORS preflight.
- **Checkpoint 4 has `kol chat request:` but no `final` event and no failure
  log** → agent ran but yielded no `final`. Check `stream_kol_research` for an
  early `return` path that skipped `final`. The success path is `yield {"type":
  "final", "data": ...}` at the end.
- **Checkpoint 4 has `kol chat failed:`** → `logger.exception` includes the
  stack trace. Read the stack to identify which tool / skill / model call blew
  up. Code field (`context_too_long` / `model_schema_error` / `agent_error`)
  is a coarse hint.

## Persistence

Reuses `picker-conversations` Insforge edge function (same table as neutral
`/research`). KOL-specific metadata lives inside the JSONB `data` field:

```json
{
  "agent_kind": "kol_research",
  "persona_username": "qinbafrank",
  ...
}
```

Frontend filters list by `data.agent_kind`. **No DB migration was required.**

## Flag gating

Chat + conversation routes are behind `require_kol_research_flag` (checks the
`kol_research_agent` feature flag, registered in `features/flags/registry.py`
with `admin_default=True`). The **Cockpit read endpoints are NOT gated** — the
`/kol/{username}` page is publicly browsable; only the chat requires the flag.
