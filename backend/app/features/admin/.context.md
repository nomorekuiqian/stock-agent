# Admin 模块

## 功能

管理后台端点，提供 CRM 和运营数据查询。

## 文件结构

- `router.py` — 管理端点
  - `GET /api/admin/whoami` — 当前登录用户是否为 admin（前端用于 gate admin UI），认证依赖 `verify_user_token_with_email`，**不**走 admin 白名单
  - `GET /api/admin/dashboard` — 用户列表分页查询，参数：`page/page_size/category/tag/search/sort_key/sort_dir`；含每用户聚合：订阅 + 互动 + ops 标签 + personal_digest 30 天聚合
  - `GET /api/admin/llm-usage?days=N` — 按天 × feature 的 LLM token 用量 + USD 估值（调 `llm-usage` edge function，附 `X-Internal-Secret`）
- `crm_router.py` — CRM 相关端点（详情页、profile 增删改、interactions、grant subscription、conversations）
- `dashboard.activity` — 30-day DAU summary sourced from `user_activities` via the `admin-activity` edge function.
- `GET /api/admin/activity?days=60` — daily activity series for admin WoW/MoM comparisons.

## 认证

除 `/whoami` 外，所有端点 `Depends(verify_admin_user)`，基于 `ADMIN_EMAILS` 白名单。`/whoami` 仅校验登录态，由响应中的 `is_admin` 字段告诉前端身份。

## 详情页端点 `/api/admin/crm/users/{user_id}` 返回字段

- `subscription` — 来自 `subscriptions list_all` 行（含 plan/status/entitlements/is_lifetime/personal_digest_count_30d/personal_digest_last_date）
- `profile` — CRM 运营档案（user_profiles 表）
- `interactions` — 人工录入交互（interactions 表）
- `contact_feedbacks` / `questionnaires` — 用户反馈
- `email_subscriptions` — Resend Segments 实时查询：`{morning_report, daily_report, weekly_report, personal_digest}`，每次详情加载消耗一次 Resend API（~550ms）
- `personal_digest` — `{count_30d, last_date}`，由 list_all 已聚合，无额外查询
- `conversations` — 最近 10 条 `picker_conversations` 元信息（不含 messages）
- `conversations_total` — 总条数
- `watchlist` — `user_watchlists` 单行：`{symbols, preferences, email, updated_at}`，无则 null
- `portfolio` — `user_portfolios` 全部行：每行含 `{symbol, shares, cost_basis, entry_price, target, stop_loss, conviction, thesis, updated_at}`，无则 []

数据从新 edge function `user-holdings`（`?action=get_watchlist|get_portfolio`）拉取。该函数无 RLS，admin 后端可跨 user_id 读。

## Agent 对话子端点

- `GET /api/admin/crm/users/{user_id}/conversations` — 全部（edge function 上限 20 条）
- `GET /api/admin/crm/users/{user_id}/conversations/{conv_id}` — 单条详情含完整 messages

注：`picker_conversations` 表无 RLS，admin 后端用 anon key + 任意 user_id 即可查任何用户对话。

## 列表端点 `/api/admin/dashboard` 增量字段

每个用户额外字段：
- `personal_digest_count_30d` / `personal_digest_last_date` — 来自 `list_all` edge function（Insforge 聚合，零 Resend 调用）
- `personal_digest_subscribed` — 来自 `entitlements` 列是否包含 `personal_digest_email`，**这是真实广播路径**（`broadcast_personal_digests` 调 `list_entitled_users("personal_digest_email")` 决定发给谁）。Resend Audience「Personal Digest Daily」是历史遗留概念，实际广播不依赖它。

表格「邮件」列：早/周/专全部用 `entitlements` 推导，零 Resend 调用，性能纯前端 O(N)。

筛选 chip 组「邮件」：`订阅专属日报` / `未订阅专属` / `Pro 早报权限` / `Pro 周报权限`，每个 chip 后显示当前匹配人数（基于全用户计算，不受其他筛选影响）。

## 性能 / 缓存（2026-06 加载优化）

- **Dashboard 已改为服务端分页/过滤/排序**：`GET /api/admin/dashboard` 优先调用 `subscriptions?action=list_dashboard`，再由 edge function 调 Postgres RPC `admin_dashboard_query`（migration: `migrations/20260610120000_admin-dashboard-pagination.sql`）。前端只持有当前页 `users`，筛选 chip、搜索、排序、翻页都会重新请求后端；后端返回 `pagination`、全局 `summary`、全局 `chip_counts` 和 `engagement`。
  - **前端契约**：不要再在 `AdminDashboard.tsx` 用全量 `data.users` 做 filter/sort/slice；`data.users` 代表当前页。复制邮箱也只复制当前页。
  - **兜底路径**：如果新 RPC/edge function 尚未部署，`router.py` 会 fallback 到旧 `list_all` 并在 FastAPI 内切页，保证页面可用；正常生产路径应走 `list_dashboard`，不能长期依赖 fallback。
  - **DB 侧职责**：`admin_dashboard_query` 负责 category、chip tags（组内 OR、组间 AND）、搜索、排序、分页、summary/facet counts。新增索引覆盖 `user_feedback` / `access_requests` 邮箱聚合和 `user_activities` 用户维度聚合。

- **`get_user_detail` 不再拉全表**（`crm_router.py`）：Phase A 用已部署的 `subscriptions` edge action `get_detail`（单用户：一次 auth.users 索引查 + subscription 行，并行）拿用户记录，`digest_stats` 拿专属日报 30 天聚合，二者与 5 个用户维度查询（profile/interactions/conversations/watchlist/portfolio）一起 `gather`。Phase B 把 Resend 邮件偏好 + 2 个反馈查询合并成一次 `gather`。原来是「`list_all` 全表扫描 → 5 查询 → Resend → 反馈」4 段串行瀑布。实测：用户记录获取从 `list_all` ~1050ms 降到 `get_detail`/`digest_stats` 并行 ~290ms。
  - **防漂移兜底**：若部署的 edge function 没有 `get_detail`（旧版本/部署漂移），自动回退到 `list_all` 扫描，页面仍可加载。
- **`cache.py` — list_all 进程内 TTL 缓存**：`list_all` 现在只用于 dashboard/详情页的防漂移 fallback。`get_list_all(loader)` 以 20s TTL + `asyncio.Lock` 做请求合并缓存。
  - **失效契约**：任何改动 subscription 行（plan/status/entitlements/access_expires_at）的写路径，写成功后须调 `cache.invalidate()`。目前 `grant_subscription` 已接。**新增 subscription 写端点时记得调用**。
- **dashboard 并行 edge 调用加 10s 超时**（`router.py`），慢聚合降级为部分数据而非整页挂 30s。
- 全局 `GZipMiddleware`（`main.py`，置于 CORS 之前使 CORS 保持最外层）压缩 list_all/dashboard 大 JSON。
- **前端**：dashboard 搜索防抖 250ms 后重新请求服务端页；分页默认 50/页（`AdminDashboard.tsx`）；用户详情页 Suspense 流式 + 骨架屏（`users/[id]/page.tsx`）。

### `subscriptions` edge function 同步状态

`backend/app/edge_functions/subscriptions.js` 已包含本轮 admin 性能所需的 edge 能力：`fetchAllChunked`（绕过 PostgREST 1000 行上限，修「只有 1000 用户」截断 bug）、并行+分页的 `list_all`、单用户 `get_detail`、懒加载 `digest_stats`、`list_all` 聚合错误透传，以及 `list_expired_access_grants`。
- `set_lifetime(false)` 只撤销 lifetime 标记，不再强制重置 plan/status/entitlements；有效 tier 由正常订阅/entitlement 规则继续决定。若运营需要“撤销即硬降级”，必须同步修改 edge function、上下文文档和测试。
- 索引：实测 interactions/user_watchlists/user_profiles 的 user_id 已全部建索引，无需补。
