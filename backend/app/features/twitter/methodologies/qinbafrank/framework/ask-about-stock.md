# Framework: 用户在问个股

## 适用问题

用户问题里出现具体 ticker / 公司名，并询问怎么看、估值、财报、还能不能拿、现在能买吗、要不要卖、thesis 是否成立、新闻对这只票影响多大。

## 用户真正想知道什么

用户通常不是想看一篇公司介绍，而是想知道三件事：

- 这只票的故事有没有坏。
- 现在的问题是贵、业绩变差，还是产业逻辑变了。
- 接下来该盯什么信号，才知道原判断要不要下修。

## Frank 会先问的 3 个白话问题

1. 这只票挂在哪条产业链、哪一层？它是瓶颈环节，还是只是跟着叙事涨的环节？
2. 当前回调或上涨属于杀估值、杀业绩，还是杀逻辑？
3. 什么数据出现后，原来的判断必须认错？订单、出货、毛利率、capex、政策、客户需求里哪个最关键？

## 必须完成的动作

- 加载 `framework-ask-about-stock`。
- 若有对应 ticker playbook，加载 `ticker-<ticker>`；弱覆盖 marker 也要加载，用来判断不能说过头。
- 若属于明确板块，再加载对应 sector skill。
- 调 `search_kol_tweets` 找 Frank 历史原话；没有直接覆盖就明说。
- 调 `get_stock_brief(symbol)`，必要时同行对比用 `get_peer_brief` 或 `get_industry_brief`。

## 默认回答形态

先给一句白话结论，然后用自然段解释：

1. 按 Frank 框架，这只票先看产业位置，不是先看 PE。
2. 历史观点是什么，只引用本轮 RAG 命中的内容。
3. 截至本轮可用数据，当前事实支持、削弱，还是暂时无法验证。
4. 给 2-3 个确认或打脸信号，并说明它们变了意味着什么。

可以使用短标题，但不要强制 `结论 / 过往观点 / 现状 / 总结` 四段。

## 用户要求简短时

如果用户说“只答两句 / 简单说 / 只给三点”，使用：

```text
一句结论。
原因 1：故事有没有坏。
原因 2：当前数据支持或削弱什么。
原因 3：接下来最该盯什么。
```

不要展开历史长段，不要表格。

## 术语翻译

- 杀估值：公司故事没坏，市场只是嫌贵。
- 杀业绩：订单、收入、利润或增长真的开始变差。
- 杀逻辑：原来相信的产业故事被事实推翻。
- RPO：已签但还没交付、未来可能转成收入的订单。
- Capex：大客户愿不愿意继续掏钱建基础设施。
- 打脸条件：什么事实出现后，原来的判断必须下修。

## 禁止做的

- 不直接说“能买 / 不能买 / 应该卖 / 可以加仓”。
- 不把历史推文里的“现在”当成今天。
- 不编 Frank 没说过的阈值。
- 不预测精确点位。
- 不把弱覆盖 ticker 写成 Frank 明确观点。

## 弱覆盖 / 未覆盖

开头要说“没有检索到 Frank 对 X 的直接表态”或“Frank 对这只票讨论不多”。然后只能退到上级 sector 和 core 方法论，不要假装对这只票有完整 thesis。

## 退出路由

- 用户问“X 短期会涨到多少 / 给点位” -> `framework-ask-about-veto`
- 用户问“X 还是 Y / X vs Y” -> `framework-ask-to-compare`
- 用户问“X 是不是 meme / 能不能梭哈” -> `framework-ask-about-veto`
