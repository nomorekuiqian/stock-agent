# Framework: 用户在比较 / 让选哪个

## 适用问题

"NVDA 还是 AMD" / "Mag4 选谁" / "Circle 还是 Coinbase" / "AI 算力 vs 加密 vs 太空" / "只能留一只" / "谁更确定" / "哪个更贴近 Frank 框架"。

## 用户真正想知道什么

用户想知道的不是两边各自介绍，而是：

- 如果按 Frank 的框架，哪一边更靠近确定性。
- 哪一边只是弹性更大，但打脸条件也更近。
- 如果必须二选一，应该用什么标准选。

## Frank 会先问的 3 个白话问题

1. 谁更靠近产业瓶颈，谁只是下游受益者？
2. 谁的需求更能被订单、客户支出、出货或监管节点验证？
3. 谁的问题更像杀估值，谁更可能演变成杀业绩或杀逻辑？

## 必须完成的动作

- 加载 `framework-ask-to-compare`。
- 涉及 ticker 时加载双方 ticker skill；没有 ticker skill 时加载上级 sector。
- 调 `search_kol_tweets`，分别检索两边或用同一个 query 覆盖两边。
- 可交易标的必须覆盖当前数据：优先 `get_stock_brief`，需要行业视角时用 `get_peer_brief` / `get_industry_brief`。

## 默认回答形态

先给对比结论，再给同一维度比较：

- 产业位置。
- 需求验证。
- 估值/业绩/逻辑风险。
- 打脸条件。

如果一边没有 Frank 直接覆盖，必须把它降级为方法论推断。

## 用户要求简短或必须选一个时

用户说“只能留一只 / 只选一个 / 只答两句”时，必须直接给出条件化选择，不要回避：

```text
如果只按 Frank 的“确定性优先”，我会把 A 排在 B 前面。原因是 A 更靠近瓶颈，B 更依赖后续兑现。
```

仍然不能写成买卖建议；这是框架内的相对排序。

## 术语翻译

- 确定性：更容易被订单、客户支出、出货或政策节点验证。
- 弹性：涨跌空间可能更大，但不代表确定性更强。
- 瓶颈：产业链里最缺、最难快速替代的环节。
- 杀逻辑：原来相信的产业故事被事实推翻。

## 禁止做的

- 不做不公平对照：不能给 A 写优点、给 B 只写缺点。
- 不把“Frank 没直接讲过”的一边说成和直接覆盖的一边同等确定。
- 不给精确点位。
- 不编 Frank 没说过的对比阈值。

## 退出路由

- 用户追问其中一个深度问题 -> `framework-ask-about-stock`
- 用户比较产业而非股票 -> 同时加载 `framework-ask-about-sector`
