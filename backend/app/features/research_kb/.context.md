# Research KB - 博主历史观点 RAG 模块

## 功能概述

基于 KOL 历史观点知识库的中文投研问答 Agent。用户提问后 Agent 用 `search_kb` 检索 Insforge `vector_chunks` (pgvector + HNSW) 中预先入库的 KOL 推文/文章片段，必要时再调用市场数据工具补充实时信息，最后用 Markdown 输出带作者+日期标注的回答。

设计上是 **tool-driven RAG**（LlmAgent 自己决定何时调 search_kb），不是经典的"预检索 + 注入 prompt"。这条路径让模型有机会按需扩查、追问，但也意味着每次回答前要严格要求模型至少调一次 `search_kb`（详见 instruction）。

## 数据流

```
用户提问 (前端 /research/kb)
  -> POST /api/research-kb/chat (Depends verify_user_token)
  -> agent.answer(message, history)
       -> reset chunks_buffer (contextvar)
       -> InMemoryRunner.run_async(LlmAgent + tools)
            -> tool: search_kb(query, k)
                 -> service.retrieve(query)
                      -> edge function vector-store ?action=embed (OpenAI text-embedding-3-small via edge)
                      -> edge function vector-store ?action=search (pgvector cosine)
                 -> chunks 写入 contextvar buffer
            -> 可选: get_market_overview / get_stock_quote / get_stock_news /
                     get_technical_analysis / get_stock_fundamentals
                     (来自 app.shared.data_tools.research_tools)
       -> 取最后一条 assistant text
       -> 返回 ResearchKBResponse(answer, chunks_used=buffer)
```

`_run_session` 包了 `asyncio.wait_for(timeout=75s)`，超时返回友好提示而不是 502。

## API 端点

| 方法 | 路径 | 认证 | 说明 |
|------|------|------|------|
| POST | `/api/research-kb/chat` | user_token | 单轮问答，body `{message, history?}`，返回 `{answer, chunks_used[]}` |

## 关键文件

| 文件 | 职责 |
|------|------|
| `agent.py` | `LlmAgent` 模块级单例 + `answer()` 入口；挂 `meter("research_kb.chat", ...)` |
| `service.py` | `retrieve(query)` — 调 vector-store edge function 的 embed + search，转 `RetrievedChunk` |
| `tools.py` | `search_kb` ADK tool + 跨调用的 chunks contextvar buffer |
| `models.py` | Pydantic：`ResearchKBRequest/Response`、`ResearchKBMessage`、`RetrievedChunk` |
| `router.py` | 单端点 `/api/research-kb/chat` |

## 模型 & Embedding

- **LlmAgent model**: `gemini-3.8-flash`（默认对话模型）
- **Embedding**: OpenAI `text-embedding-3-small` (1536 维)，**由 edge function 内部调用 OpenAI**，后端不直连
- **检索参数**: `match_count=6` (range 3-12)，`match_threshold=0.3` (cosine 距离，对应相似度 0.7；当前阈值偏低，待真实命中数据反馈后再调)

## Insforge 数据表

`vector_chunks` (pgvector + HNSW)，由运营离线灌入；本 feature 只读：

| 字段 | 用途 |
|------|------|
| `id` | UUID PK |
| `content` | 片段正文 |
| `title` | 用于回答里标注 "@author (date)" |
| `source_type` | 来源类型，可作 filter（当前未启用） |
| `source_id` | 原始推文/文章 ID，用于前端去重显示 |
| `url` | 原文链接 |
| `embedding` | vector(1536) |

灌库脚本不在本模块内，由运营/管理员通过独立的 ingestion 流程维护。

## 注意事项

- **`search_kb` 必须挂在 instruction 的"工作流"第一步**：模型很可能跳过检索直接答事实，会让 KB 失去意义。当前 prompt 用粗体 + 重复强调。
- **chunks_buffer 用 contextvar**：模块级 LlmAgent 在并发请求下共享，但每个 `answer()` 进入时显式 `reset_chunks_buffer()` + `_chunks_buffer.set([])` + 后续 in-place 追加。原因：ADK 工具运行在子 task 里，contextvar 子→父不传递；我们靠 list 对象 mutation 让父能拿到。
- **超时是 75s**：长于 router 默认 60s 是有意的，因为 search_kb 可能要 1-2 次 + 至少一次 market 工具。如果还超时再考虑 streaming。
- **user_id 当前硬编码 `"research_kb"`**（不是真实用户 ID）—— 留作 TODO，影响 ADK session 日志归因，不影响功能。
- **不开放 GET endpoint**：KB 列表查询当前不需要（只有一个隐式 KB），不暴露 `/kbs` 端点。
- **架构边界**：跨 feature 工具（market_overview/quote/news/technical/fundamentals）全部走 `app.shared.data_tools.research_tools`，不要直接 import `screener.*`，否则 `test_no_cross_feature_imports` 会挂。
