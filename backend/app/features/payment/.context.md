# Payment 模块

## 功能

Stripe 订阅支付 + Entitlements 权限管理。Stripe 是账单与新订阅真相源，Insforge `subscriptions.entitlements` 列是应用权限缓存。正式销售层只有 Pro / Max；历史 `ultra`、`creator_max_qinbafrank` 和 `kol_pack_qinbafrank` 只作为 legacy 输入/数据兼容，归一化为 Max。

## 架构 (四层数据流)

```
Layer 1: Stripe (真相源)
  Customer → Subscription → Active Entitlements (Pro 8 / Max 11 个 feature)
       |
       | webhook + compensation sync
       v
Layer 2: Insforge subscriptions 表 (快速读缓存)
  entitlements JSONB 列 + 5 分钟内存 TTL
       |
       | 同一 webhook handler 顺序写
       v
Layer 3: Resend Segments (发送缓存)
  sync_resend_segments(email, entitlements) — 唯一写入点
       |
       v
Layer 4: Frontend EntitlementsContext
  has(feature) 判断，PaywallGuard requiredFeature
```

## API 端点

| 端点 | 方法 | 认证 | 描述 |
|------|------|------|------|
| `/api/payment/checkout-session` | POST | Bearer | 为新订阅创建 Stripe Checkout Session |
| `/api/payment/checkout-session/complete` | POST | Bearer | Checkout 回跳后校验 session_id 并同步 subscription/entitlements |
| `/api/payment/subscription-status` | GET | Bearer | 查询用户订阅状态 (`?fresh=true` 旁路 5 分钟缓存)，返回当前 Stripe subscription item 的实际计费价格字段 |
| `/api/payment/me/entitlements` | GET | Bearer | 查询用户 feature entitlements (`?fresh=true` 旁路缓存并补偿同步 Stripe Subscription) |
| `/api/payment/portal-session` | POST | Bearer | 创建 Stripe 管理 Portal；传 `product` 时用于已有订阅升级确认 |
| `/api/payment/cancel-subscription` | POST | Bearer | 将当前用户 Stripe 订阅设置为周期末取消；primary 账户找不到时 fallback 到 `STRIPE_LEGACY_SECRET_KEY` 对应旧账户 |
| `/api/payment/reconcile-expired-grants` | POST | Cron | 清理过期的非 Stripe grant (`access_expires_at`) |
| `/api/payment/webhook` | POST | Stripe Signature | Webhook 回调；依次用 primary(`STRIPE_WEBHOOK_SECRET`) 再 legacy(`STRIPE_LEGACY_WEBHOOK_SECRET`) 验签，按命中的密钥决定下游 Stripe 调用用哪个账户 key（双账户共存期旧账户事件也能同步） |

## 文件结构

- `router.py` — 路由 + Webhook (checkout.session.completed / subscription.updated / subscription.deleted / entitlements.active_entitlement_summary.updated)。Webhook 双账户验签：`webhook_accounts` 顺序尝试 primary→legacy 签名密钥，命中后把对应 `event_api_key` / `event_account_ref` 透传给 `stripe.*` 调用与 `sync_subscription_from_stripe` / `sync_entitlements_from_stripe`
- `entitlements.py` — Entitlements Gateway (`has_entitlement` / `get_user_entitlements`，普通用户查 entitlements 列；lifetime 用户返回 MAX_FEATURES，忽略 legacy KOL pack key)
- `service.py` — Stripe API 封装 (checkout / portal / customer 管理 / entitlement reconciliation / expired grant reconciliation)
- `models.py` — Pydantic 模型
- `db.py` — subscriptions Edge Function 操作 + 缓存 + `get_subscription_by_customer`。`get_subscription()` 只有在 Edge Function 明确返回 `success=true,data=null` 时才表示 free/no row；超时、502、`success=false` 会抛 `SubscriptionLookupError`，调用方必须返回 503 或显式处理，不能把失败降级成 free。Production subscription reads 使用 fresh HTTP client + 8s timeout，避免 Railway 上 stale pooled connection 把登录后的权限读取拖到 30s/60s。

## 依赖

- `stripe` SDK (同步调用通过 `asyncio.to_thread` 包装)
- Edge Function: `subscriptions` (get / get_by_customer / upsert)
- 环境变量: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRO_PRICE_ID`, `STRIPE_MAX_PRICE_ID`。`STRIPE_LEGACY_SECRET_KEY` 用于迁移期对旧账户订阅执行自助取消 fallback **及 webhook 处理旧账户事件时的下游 API key**；`STRIPE_LEGACY_WEBHOOK_SECRET` 是旧账户 webhook endpoint 的签名密钥，webhook handler 用它验证旧账户发来的事件（缺失则旧账户事件全部验签失败、取消/降级不同步）；`STRIPE_ULTRA_PRICE_ID` 仅用于迁移期识别旧 Stripe price。Stripe-to-Stripe 迁移脚本必须优先使用 `STRIPE_MIGRATION_SOURCE_SECRET_KEY` / `STRIPE_MIGRATION_DESTINATION_SECRET_KEY` 和可选 `STRIPE_MIGRATION_DESTINATION_PRO_PRICE_ID` / `STRIPE_MIGRATION_DESTINATION_MAX_PRICE_ID`，不要直接复用本地开发用的 `STRIPE_SECRET_KEY`。

## Ultra -> Max 迁移

Ultra 已取消，Qinbafrank / 博主研究室权益并入 Max。生产迁移先跑 dry-run 导出 snapshot，再确认后 apply:

```bash
cd backend
source venv/bin/activate
python scripts/migrate_ultra_to_max.py
python scripts/migrate_ultra_to_max.py --apply
```

脚本默认只读，输出 `backend/tmp/ultra-to-max-migration/*.json`。它会把 active/trialing Stripe legacy Ultra、lifetime Ultra、未过期 Ultra grant 目标设为 `plan=max` + `MAX_FEATURES`；把已过期或 inactive legacy rows 清成 Free/expired；并标出仍在 Stripe Ultra price 上、需要人工移动到 Max price 的 subscription。

## 注意事项

- `entitlements.active_entitlement_summary.updated` 是权限变更的权威触发源；`checkout.session.completed`、`customer.subscription.updated`、`customer.subscription.deleted` 也会调用同一个 `sync_entitlements_from_stripe()` 作为补偿路径，避免 webhook 顺序/投递导致本地 entitlements 漂移
- entitlements webhook 检测档位后**补全为代码定义的完整 tier 集合**（Pro=`PRO_FEATURES` 8 项 / Max=`MAX_FEATURES` 11 项）再写入，不逐项照搬 Stripe：Stripe 不会把订阅创建后才挂到 product 的 feature 追溯给老订阅，故 tier 内容以代码 catalog 为权威（与 lifetime 一致），档位判定仍以 Stripe 为准
- `has_entitlement()` 对普通用户无 fallback — entitlements 列为空则无权限。Lifetime 用户例外：固定拥有 MAX_FEATURES。
- Checkout success_url 指向 `/pricing/success?checkout=success&tier={pro|max}&product=...&next=...&session_id={CHECKOUT_SESSION_ID}`；成功页先调用 `/checkout-session/complete` 主动同步，再轮询 `subscription-status?fresh=true` + `me/entitlements?fresh=true`，确认目标 entitlement（Max=`ai_research_engine`）落库后才跳回 `next`。历史 `tier=ultra` / `product=creator_max_qinbafrank` 会在成功页和后端归一化为 Max。
- Checkout/Portal return URL 优先使用发起请求的合法 `Origin`（`ALLOWED_ORIGINS` 或 `CORS_ALLOWED_ORIGIN_REGEX` 匹配），否则回退 `FRONTEND_URL`。这是为了 Vercel preview 多域名测试时回到同一个 origin，避免 localStorage/cookie 登录态在跨 preview 域名回跳后丢失；不能接受任意 origin，避免开放跳转。
- `POST /api/payment/checkout-session` 正式支持 `tier=pro|max`；历史 `tier=ultra` 和 `product=creator_max_qinbafrank` 仅作为兼容 alias 归一化为 Max。当前只支持 `billing_interval=monthly`。
- 新订阅 Checkout 已启用 Stripe Tax：创建 Session 时传 `automatic_tax.enabled=true`，要求 `billing_address_collection=required`，并通过 `customer_update.address/name=auto` 把 Checkout 收集到的账单地址和名称写回 Stripe Customer；`tax_id_collection.enabled=true` 允许支持地区的企业客户填写 business tax ID。Stripe Tax 只会在已配置 active tax registration 的辖区实际征税，未注册地区可能显示 0 tax。
- 新付费用户走 Checkout；已有 Pro 订阅用户升级 Max 时前端通过 `/portal-session` 打开 Stripe Billing Portal `subscription_update_confirm` flow，避免创建第二个订阅。升级 Portal session 会确保使用 `proration_behavior=always_invoice` 的 Billing Portal configuration，让 Stripe 立即按剩余周期补差价。后端 `/checkout-session` 也会兜底检查真实 paid subscription：同级/降级请求返回 409，升级请求返回 Portal URL（沿用 `checkout_url` 响应字段）而不是创建新的 Checkout Session。Portal flow 完成后回 `/pricing/success`，由 `subscription-status?fresh=true` 从 Stripe Subscription 刷新本地状态。
- `STRIPE_PRO_PRICE_ID` / `STRIPE_MAX_PRICE_ID` 应在生产环境显式配置；代码在变量缺失或配置 Price inactive 时会尝试用 Stripe Price lookup key `themarketbrew_<tier>_monthly` 兜底解析 active monthly Price。`STRIPE_ULTRA_PRICE_ID` 迁移期保留，只用于把旧 Stripe subscription 识别并同步为 Max。
- `checkout.session.completed`、`customer.subscription.updated` 和 `subscription-status?fresh=true` 都会把 Stripe subscription price/metadata 解析成 app tier，并写入代码 catalog 定义的完整 entitlements；随后再尝试用 Stripe Active Entitlements 对齐，避免 entitlement webhook 延迟导致购买后长时间不可用。
- Stripe Portal 周期末取消时 Stripe 仍可能保持 `status=active`，但返回 `cancel_at`（部分 API 版本下 `cancel_at_period_end` 可能为 false）。`sync_subscription_from_stripe()` 会把 `cancel_at_period_end`、`cancel_at`、`canceled_at` 写入 `subscriptions` 并由 `/subscription-status` 返回，前端据此展示“已取消 / 权益有效至”。
- `sync_subscription_from_stripe()` 还会从 Stripe subscription item 的 Price 提取 `stripe_price_id`、`billing_amount_cents`、`billing_currency`、`billing_interval`、`billing_interval_count`，写入 `subscriptions` 并通过 `/subscription-status` 返回。Profile 订阅卡必须优先显示这些真实计费字段，避免早鸟价/历史价用户被当前公开价格误导。
- 如果 `stripe_customer_id` / `stripe_subscription_id` 属于迁移前的 Stripe 账户，`create_portal_session()` 会先验证 primary 账户 subscription 是否存在；找不到时用 `STRIPE_LEGACY_SECRET_KEY` fallback 到旧账户创建 Customer Portal session，让前端同一个“管理订阅”入口能按账号分流。`subscription-status?fresh=true` 也会按相同顺序刷新旧账户 subscription，并把本地行标记为 `stripe_account_ref=legacy_2026` / `stripe_migration_state=legacy_active`。用户自助取消仍可走 `/cancel-subscription`，该 endpoint 同样先尝试 primary，再用旧账户设置 `cancel_at_period_end=true`，并把 `stripe_migration_state=legacy_cancel_scheduled` 写回本地。
- Stripe-to-Stripe migration 上传前，先用 `python scripts/prepare_stripe_account_migration_customers.py --customer-map <csv>` 检查目标账号 customer 付款方式。脚本默认 dry-run，输出 `payment-readiness-current-*.csv/json`、`pan-copy-remaining-customer-ids-*.csv`、`pan-copy-remaining-customer-ids-dashboard-*.csv` 和 `manual-default-payment-method-required-*.csv`；只有显式 `--apply-defaults` 时才会在目标账号把唯一安全候选 payment method/source 设为默认，不会创建订阅或扣款。优先把 `pan-copy-remaining-customer-ids-dashboard-*.csv` 上传到 Stripe Dashboard 的 PAN copy partial CSV upload；`customer` header 版本保留给脚本/旧工具兼容。
- 任意阶段可用 `python scripts/status_stripe_account_migration.py --customer-map <csv>` 做只读总览；它会串行跑 payment readiness、preflight、导出覆盖率、目标账号 subscription metadata mapping discovery，以及 Billing toolkit 的 subscription schedule discovery，并输出 `migration-status-*.json`。mapping/schedule discovery 使用 Stripe list pagination，默认最多扫描 500 个目标对象，可用 `--discover-limit` 调整。报告顶层 `next_action` 会给出当前 phase 的下一步动作、命令、artifact 和禁止事项。`phase=awaiting_pan_copy` 表示只能先做 PAN copy；`phase=ready_for_billing_toolkit` 才能重新导出并上传 toolkit CSV；`phase=post_import_scheduled` 表示 toolkit 已创建 scheduled subscription schedules、但还不能回写本地；`phase=post_import_reconcile_ready` 表示目标账号已能发现新订阅 mapping，或所有 discovered schedules 都已有新 subscription id，可以进入 dry-run reconcile。完整操作 runbook 见 `docs/plans/active/stripe-account-migration.md`。
- Stripe-to-Stripe migration 上传前，还要用 `python scripts/preflight_stripe_account_migration.py --customer-map <csv>` 做只读自检：检查 Stripe keys、`subscriptions?action=list_all` 字段、活跃订阅数量、customer map 覆盖、目标账户 Product ID、目标 customer 默认付款方式、源账户订阅抽样。CLI 默认要求 source/destination 都是 live key；只有 sandbox 验证时才加 `--allow-test-mode`。默认会从 `STRIPE_MIGRATION_DESTINATION_PRO_PRICE_ID` / `STRIPE_MIGRATION_DESTINATION_MAX_PRICE_ID`（fallback 当前 Pro/Max Price ID）分别解析目标 Pro/Max Product；也可显式传 `--adhoc-product-id <prod_id>` 强制所有 ad-hoc migrated prices 使用同一个 Product。
- 如果 preflight 报告里有 `already_destination_candidates` 或 `source_inactive_local_candidates`，先运行 `python scripts/repair_stripe_account_migration_local_state.py` 看 dry-run 报告。确认无误后可加 `--apply`：已在目标账号 active 的 row 会同步目标 subscription/customer/billing 字段；源账号已 canceled 且目标账号按 email 没 active subscription 的 row 会标记为 Free/canceled。脚本不会复制付款方式、不会创建订阅。
- Preflight 通过后，用 `python scripts/export_stripe_account_migration.py --customer-map <csv> --include-cancel-scheduled` 从本地订阅和旧账户 Stripe subscription 生成 Billing migration toolkit CSV。它默认只读、保留早鸟价/历史价为 ad-hoc migrated prices、要求旧 customer -> 新 customer 映射，并把不安全行写进 `.report.json`。不要把本地 active test key 作为目标账号；脚本会默认拒绝 test-mode key。Live toolkit CSV 的 `start_date` 必须在上传时至少 24 小时后，所以 PAN copy 完成后要重新导出，不要复用过期 CSV。
- Stripe-to-Stripe migration live 后，可先用 `python scripts/reconcile_stripe_account_migration.py --discover-schedules --output <csv>` 查看 Billing toolkit 已排期但尚未 go-live 的 subscription schedules；pending schedule 只能观察，不能回写本地。如果 discovered schedules 全部已有 `new_stripe_subscription_id`，该 CSV 可作为 reconcile mapping 输入；`--strict-metadata` 会回查 Stripe subscription schedule，确认 schedule metadata、new subscription id、user_id 与 mapping 一致，不会单纯信任 CSV；schedule 校验通过时，dry-run 报告展示 schedule 验证后的 metadata，避免目标 subscription metadata 缺失或错误时误读。目标 subscription active/trialing 后，也可用 `python scripts/reconcile_stripe_account_migration.py --discover-mapping --output <csv>` 从目标账号订阅 metadata 自动生成 old->new subscription mapping。再用 `python scripts/reconcile_stripe_account_migration.py --mapping <csv> --apply` 将新账户 subscription/customer id 回写到 `subscriptions`。CSV 至少包含 old subscription id 和 new subscription id；脚本会使用 `STRIPE_MIGRATION_DESTINATION_SECRET_KEY` 验证新订阅 active/trialing、可选校验 metadata/金额/Portal，并把旧 id 保存到 `legacy_stripe_subscription_id`。确认目标订阅 active 且本地回填成功后，才可额外传 `--cancel-source-at-period-end` 把旧账号 subscription 设为周期末取消，避免双重续费；该参数会同时要求 source/destination live key。
- `kol_pack_qinbafrank` 出现在 Stripe Active Entitlements 时，后端归一化为 `plan=max` + `MAX_FEATURES`；该 key 不再写入 active app entitlements。
- 老 `plan=ultra` row 在 `sync_subscription_from_stripe()` 和 `sync_entitlements_from_stripe()` 中归一化为 `plan=max` + `MAX_FEATURES`。Stripe 非 active / 空 active entitlement / subscription.deleted 仍会正常清空权限。
- Stripe entitlement reconciliation 写入 `plan/status/entitlements` 时会同时清理旧的 `access_expires_at`，避免历史 trial/admin grant 的过期字段拦住已付费用户
- 过期的非 Stripe grant 由读时 `access_expires_at` 判断兜底；`POST /api/payment/reconcile-expired-grants` 负责把已过期 grant 的 `plan/status/entitlements` 清理成 Free/expired，并同步 Resend；edge function 查询失败必须向 cron 暴露失败，不能当作空结果
- 新试用建议优先通过 Stripe Trial Subscription 实现，到期自动 cancel + webhook 清权限；旧的 `access_expires_at` grant 保留 reconciliation 兜底

## Lifetime 终身用户

`subscriptions.is_lifetime: true` 的用户绕开整条 Stripe 链路：
- webhook / reconciliation 进入函数后会跳过 `is_lifetime=true` 用户，不写库
- `has_entitlement()` / `get_user_entitlements()` 检测 is_lifetime=true 时返回完整 MAX_FEATURES，不 union legacy `kol_pack_qinbafrank`。
- 开通工具：`python -m scripts.grant_lifetime <email>`（`--revoke` 取消）。撤销会清空 `plan/status/access_expires_at/entitlements`，避免旧 Max entitlements 残留。
- DB 字段：`is_lifetime BOOLEAN DEFAULT FALSE`
- 权限模型：`docs/constraints/subscription-model.md`
