# Feature Flags Module

Per-user feature flags for gradual rollout / canary testing.

## Architecture

`feature_flags` 表 (Insforge) → `feature-flags.js` Edge Function → `db.py` →
两条路由：

- **用户读**: `router.py` → `GET /api/flags` （`verify_user_token`）
- **管理员写**: `admin_router.py` → `GET/POST/DELETE /api/admin/flags` （`verify_admin_user`）

flag key 的存在性由 **代码** 定义 —— `registry.py::KNOWN_FLAGS` 是唯一信源：

- 前端 `/admin/flags` 下拉里能选的 flag 来自这里（`GET /api/admin/flags` 返回 `known_flags`）。
- 后端 POST/DELETE 在写之前用 `is_known_flag()` 校验，避免错字写入。

新增 / 退役 flag 的完整流程见 [../../../../docs/guides/feature-flags-playbook.md](../../../../docs/guides/feature-flags-playbook.md)。

## Key Constraints

- 写操作必须走 `verify_admin_user` 保护的 `/api/admin/flags`；手动 SQL 仍是 EF 挂掉时的兜底路径，但日常运营不应使用 —— admin UI 会拦截 typo。
- Edge Function 本身无 auth — 安全由 FastAPI 层 `verify_user_token` / `verify_admin_user` 保证。
- 读路径在任何失败时返回空集合（safe fallback，业务继续走旧分支）；写路径在 EF 失败时返回 HTTP 502，让运营立刻看到。
- 表无 RLS（与其它 EF 访问的表一致）。
- 设计决策：管理界面只暴露"添加 / 删除"，不暴露 `enabled=false` 切换 —— 数据库列保留以便未来扩展，但当前 admin 看到的视图统一过滤 `enabled=true`。

| `pandacircle_persona` | 潘大的科技交流圈 KOL persona（/research RAG）— `emails=` 白名单，仅指定测试账号 | 2026-06 | tester 灰度 |

*要新增 flag：在 `registry.py` 里加一行 `FlagDef("xxx", "...")`，然后按 playbook 接入分支。三种授予方式可叠加并取并集（见 `db.get_user_flags`）：① `admin_default=True` 让 `ADMIN_EMAILS` 用户无需 DB 记录即命中（`registry.admin_default_flags()`）；② `emails=("a@x.com", ...)` 把 flag 精确开给指定邮箱，非 admin 也行、无需 DB 行（`registry.email_allowlisted_flags()`）；③ 通过 `/admin/flags` 给某 user_id 写 DB 行。*

> `pandacircle_persona` 的 gate 实现在 `features/kol_research/router.py`：`_FLAG_GATED_PERSONAS` 映射 persona→flag，`GET /personas` 过滤掉无 flag 的 gated persona，`/chat` 与 `/chat/stream` 在配额前 `_ensure_persona_allowed` 拦 403。新增"仅测试账号"的 persona 照此模式即可。

> `/admin/flags` 某用户「添加」列显示「全部已开通」无按钮是**预期**——下拉只列他还没开通的已知 flag；目前只有 `for_you_v2` 一个，已开通即收起。详见 playbook §6 故障速查。
