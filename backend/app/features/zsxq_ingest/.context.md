# zsxq_ingest — Panda 知识星球 采集→归一化→入库 pipeline

自动化把 潘大的科技交流圈（`group_id 15554581218512`）的内容爬取、归一化、向量入库，定时执行。
设计 spec：`docs/plans/active/panda-zsxq-pipeline-automation.md`；实现 plan：`...-impl.md`。

## 为什么是 cookie 爬虫（不要再试官方 API）
该星球**关闭了官方 API**：作为普通成员（账号「金黄」），官方 MCP/`zsxq-cli` 调任意内容都返回「仅限成员在星球内查看，暂不支持通过 API 访问」。只能用浏览器成员 session cookie 走内部接口 `api.zsxq.com/v2/...`。cookie / 会员会过期 → 邮件通知管理员刷新（唯一人工环节）。

## 模块结构
- `crawl.py` — cookie zsxq API client。忠实移植现有 crawler 机制：游标 ms-offset、`smart_delay`（页间 2–5s）、每 15 页长休眠 180–300s、错误分流（401→`cookie_expired` / 403→`access_denied` / 14210→`membership_expired` 抛 `ZsxqAuthError`；429→`ZsxqRateLimitError`；anti-crawl 1059→退避重试 ≤10 次 2/5/10s）、评论 `comments_count>8` 才分页拉、二进制下载。**长文 article**：`talk.text` 只是截断预览（以「…」结尾），完整正文在 `talk.article.{inline_article_url,article_url}`，`fetch_article_text()` 用 cookie 抓 HTML→`_extract_article_text()` 提纯文本（剥脚本/标签、去重标题、剪掉 join_group 页尾 CTA）。**不做存储**（返回字节/文本，由 service 上传/注入）。
- `normalize.py` — 单条 raw zsxq JSON → threads.jsonl 记录；复用 `export_corpus` 的 `clean_text`/`<e>` 标签渲染。**标签来自 `talk.text` 内的 `<e type="hashtag">`，没有顶层 hashtags 字段**。**长文 body**：service 把完整文章塞进 `talk.full_article_text`，normalize 的 body 优先用它（否则只入库 ~600 字截断预览）；标签仍取自预览的 `<e>` 标签。外链（`<e type="web">`）的 href 抽进 `rec.external_links`（仅作 citation metadata，**不抓外部正文**）。**球主评论区参与救回**：成员发起的帖若 **owner 在评论区有实质回复**（`_meaningful_len ≥ 8`，排除点赞/表情/「好的」），则把该帖**重新归属给 owner**、正文=owner 回复+原帖上下文（`kept_via_owner_comment` 标记）；否则成员帖被丢弃。
- `indexing.py` — 从 `scripts/index_zsxq_threads.py` 抽出的可复用 service：`prepare_records`（eligibility=owner/creator、Tier-0 enrichment、ticker 词典）、`audit_distribution`、`index_prepared`（走 `features.vector.service`）。CLI 仍是薄封装。
- `service.py` — 异步编排 `run_ingest`：读 cookie → 爬（写 raw archive + 二进制到 bucket + 长文抓 `fetch_article_text()` 注入 `talk.full_article_text`、计 `articles_fetched` + 逐 thread 写 ledger）→ **`client.fetch_creator_ids()` 取官方角色**（owner+admin_ids+guest_ids+partner_ids;成员发的帖 role=member 被 `_eligible` 丢弃——zsxq 成员也能发帖，不能"谁发帖谁算 creator"；取角色失败则 fallback 仅 owner）→ normalize → audit gate → index → smoke。`gate_should_block`、`_notify_auth_failure`。**二进制上限**：Insforge storage 网关拒绝 >~20MB 请求体（HTTP 413），故 `MAX_BINARY_UPLOAD_BYTES`（~20MB）以上的附件**确定性跳过**，`stage_binaries` 据实记 `partial`（未归档数计入 `binaries_failed`）；正文仍入库，不影响检索。
- `db.py` — 调 `zsxq-ingest-store` edge function 读写 4 张表（含只读 `list_runs`：最近 runs，给监控视图 + 并发护栏用，失败降级返回 `[]`）；`upload_binary`/`list_objects`/`download_object`（后两者供 article 回填枚举+读取 raw archive）走 **InsForge S3 兼容网关**（`/storage/v1/s3`，boto3 SigV4 path-style）+ **最小权限 scoped S3 key**（`INSFORGE_S3_ACCESS_KEY_ID`/`SECRET`，仅存储权限，非全权 `INSFORGE_API_KEY`）。boto3 同步调用包在 `asyncio.to_thread`。
- `router.py` — `POST /api/zsxq/ingest`（cron secret，accepted 异步）、`POST /api/zsxq/backfill`（cron secret，异步，修历史截断 article。两模式共用 `_backfill_one_topic`：删旧 doc + 拉全文 + `force` 重建。**默认**读 bucket archive（`topics/`+`raw/`，`backfill_articles`）——只覆盖被归档的 service-crawl 帖；**body `{source_ids:[...]}`** 走 `backfill_articles_by_ids`，按 id 调 `fetch_topic_by_id`（`GET /topics/{id}`）——修从本地导入、从未归档的帖。`limit` 限回填条数）、`GET /api/zsxq/runs/{run_id}`（cron secret）、`POST /api/zsxq/cookie`（admin）。**并发护栏**：增量触发若已有「新鲜」running run（`started_at` < `_ACTIVE_RUN_MAX_AGE_MIN`=120min）则跳过、不建 run 行、返回 `accepted:true, skipped:true`（cron 步骤不算失败）；`full=true` 是管理员显式覆盖、绕过护栏；过期/卡死的 running 行不阻塞。防 4h 定时把多次爬叠在同一 cookie 上。
- edge function：`app/edge_functions/zsxq-ingest-store.{js,sql}`（actions: get/set_credential、get/update_state、create/update/get_run、**list_runs**(只读)、upsert_ledger、aggregate_ledger、put_object、get_object_url）。cron：`cron-trigger.js` 的 `zsxq_panda_ingestion` job。**改了 .js 需 `insforge functions deploy zsxq-ingest-store` 才生效**。

## 不变量
`source_type=zsxq_thread`；`metadata.author_username=pandacircle`（检索 pin）；真实子作者在 `source_author_username`；Tier-0 deterministic（无 LLM）；embedding 走现有 vector service；不碰 `pandacircle` corpus binding；不写 `kol_tweets`。

## Bucket 命名（`zsxq-archive`，顶层前缀=数据类别，避免数据沼泽）
- `topics/zsxq/{group}/{YYYY-MM-DD}/topic-{id}.json` — **抓取**的 topic 原始 JSON
- `attachments/zsxq/{group}/{topic}/{filename}` — **下载**的附件（用户上传的二进制）
- `normalized/zsxq/{group}/{run_id}/threads.jsonl` — 派生/归一化导出
> 2026-06-24 起新方案（旧对象仍在 `raw/zsxq/...` 下，going-forward 不迁移）。`topics/` vs `attachments/` 明确区分「抓取数据」与「下载文件」。

## 运维 Runbook（人工步骤——本仓代码不自动部署）
> 用 `insforge-cli` skill 操作 Insforge 基础设施。
> **状态（2026-06-22）**：Insforge 侧 S0–S5 **已 provisioned**（bucket `zsxq-archive`、4 表、edge fn `zsxq-ingest-store`、`cron-trigger` 加了 job、secrets 齐）——**步骤 1–4 已完成，勿重复**。剩余：**注入 cookie**（步骤 5，需后端先部署）→ **小批量验证** `?limit=10`（步骤 7）→ **建 Schedule**（步骤 6，必须在验证后，因首跑 seed 游标）。详见 `docs/plans/active/panda-zsxq-insforge-rollout.md`「执行状态」。
> **安全兜底**：增量跑若无游标且未传 limit，自动限 `_FIRST_RUN_SAFETY_LIMIT=50`，防误触发全量爬。显式 `full=true` 或 `limit=N` 可覆盖。

1. **建 bucket**：创建 `zsxq-archive`（`insforge storage buckets` 查看 / admin API 创建）。
2. **建表**：`insforge db sql -f backend/app/edge_functions/zsxq-ingest-store.sql`。
3. **部署 edge functions**：`insforge functions deploy zsxq-ingest-store` 和 `insforge functions deploy cron-trigger`。
4. **环境变量**（后端 Railway）：`CRON_SECRET`、`EDGE_FUNCTION_SECRET`、`INSFORGE_BASE_URL`/`INSFORGE_ANON_KEY`/`INSFORGE_SERVICE_KEY`、`RESEND_API_KEY`、`ADMIN_EMAILS`、`BACKEND_URL`、`VECTOR_EMBEDDING_MODEL`。
5. **注入 cookie**：浏览器登录知识星球 → F12 Network → 任一 `api.zsxq.com` 请求 → 复制 `Cookie`（含 `zsxq_access_token`）→ `POST /api/zsxq/cookie`（admin token，body `{"cookie":"...","by":"<you>"}`）。
6. **建 Schedule**：Insforge 每日定时 POST `cron-trigger?job=zsxq_panda_ingestion`，带 `X-Internal-Secret`。
7. **首次全量回补**（谨慎，慢——可能数小时）：`POST /api/zsxq/ingest?full=true`（cron secret）；用 `GET /api/zsxq/runs/{run_id}` + 查 `zsxq_thread_ledger` 跟踪进度（断点续爬靠游标）。
8. **⚠️ 部署期校验（Appendix A 未决项）**：首次 `put_object` 后，确认 Insforge storage SDK 真实返回 `{data:{url,key}}`。若 shape 不同（如 `{path,fullPath}`），改 `zsxq-ingest-store.js` 的 `put_object` 返回映射，否则 `url/key` 会是 null。
9. **检索冒烟**：对一个有覆盖的 ticker 跑 `search_kol_tweets`，确认返回知识星球 chunk，且引用显示真实子作者（非全 pandacircle）。

## cookie/会员过期处理
爬虫遇 401/403/14210 → `zsxq_credentials.status` 标记 + run `auth_failed` + Resend 邮件给 `ADMIN_EMAILS`。管理员按邮件指引重新 `POST /api/zsxq/cookie`（401/403 换 cookie；14210 先续费星球成员再换 cookie）。下次 cron 自动恢复。**邮件去重**：邮件只在 active→失效的**爬取时转换点**发一次；之后被 Step-1 凭据检查挡下的 tick **不再重发**（否则 4h 定时会每天 ~6 封轰炸管理员），持续失效状态靠监控视图体现。
