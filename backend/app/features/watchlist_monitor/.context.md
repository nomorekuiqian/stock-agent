# Watchlist Monitor - AI 监控台

## 功能概述

V0 将“专属日报”拆成 ticker-first 的共享分析缓存。后台对 ticker 生成 `ticker_daily_briefs`，用户打开 `/for-you/monitor` 时只读取自己 watchlist 对应的 cached briefs，不在 read path 里跑 LLM。

核心问题只回答三件事：

- 这只股票今天是否需要关注。
- 为什么需要关注。
- 未来 14 天要看什么。

## API 端点

| 端点 | 方法 | 描述 | 认证 |
|------|------|------|------|
| `/api/watchlist-monitor` | GET | 读取当前用户 watchlist monitor | Bearer Token (`verify_user_token`) + `for_you_website` entitlement |
| `/api/watchlist-monitor/backfill` | POST | 为当前用户单独补生成缺失/过期的 watchlist briefs；只扫描该用户 watchlist，不触发 paid universe | Bearer Token (`verify_user_token`) + `for_you_website` entitlement |
| `/api/admin/watchlist-monitor/generate-active-tickers` | POST | 按显式 symbols 或 `user_id` watchlist 生成 briefs | Cron Secret (`verify_cron_secret`) |
| `/api/admin/watchlist-monitor/generate-paid-universe` | POST | 合并所有拥有 `for_you_website` entitlement 用户的 watchlist，按去重 ticker universe 批量生成 briefs | Cron Secret (`verify_cron_secret`) |
| `/api/admin/watchlist-monitor/start-paid-universe` | POST | 为生产 cron 启动 paid universe 后台生成任务并快速返回，避免 InsForge Edge Function 网关等待全量生成超时 | Cron Secret (`verify_cron_secret`) |
| `/api/admin/watchlist-monitor/generate-test-universe` | POST | Dry-run 阶段专用：只合并 Voya + owner 两个测试账号的 watchlist 并集并生成 briefs | Cron Secret (`verify_cron_secret`) |

生成请求：

```json
{
  "symbols": ["NVDA", "TSLA"],
  "user_id": "optional-user-id",
  "limit": 5,
  "force": false
}
```

用户 backfill 请求：

```json
{
  "symbols": ["NVDA", "TSLA"],
  "limit": 25
}
```

`symbols` 可为空；为空时后端从当前用户 watchlist 中找缺失项。该 endpoint 不接受 `force`，且只会 queue 没有今日 brief、brief 过期或缺少 `market_discussion` cache 的 ticker。用户传入的 ticker 也必须属于自己的 watchlist，否则只会进入 `skipped_symbols`，不会生成。

测试 universe 生成请求：

```json
{
  "user_ids": ["fa726347-f49a-4fee-973e-a3b69fdcbdd4", "d00a6201-646a-489f-95a2-aff8f90fe669"],
  "limit_per_user": 25,
  "max_symbols": 50,
  "force": false,
  "dry_run": false
}
```

`user_ids` 为空时默认只跑 Voya (`voya.technologies@gmail.com`) 和 owner (`kedengpan@gmail.com`) 两个 app 用户。正式 paid beta 上线后不再使用 watchlist monitor 专用 feature flag；测试 universe 端点仅受 cron secret 保护。`dry_run=true` 只返回两个账号 watchlist 的去重并集，不触发 LLM。

Paid universe 生成请求：

```json
{
  "user_limit": 1000,
  "limit_per_user": 25,
  "force": false,
  "dry_run": false
}
```

Paid universe 使用 `subscriptions` Edge Function 的 `list_entitled` action 查询 `for_you_website` entitlement 用户，把这些用户 watchlist 里的 ticker 全量去重后生成共享 brief；不再配置 ticker 数量上限，也不会按用户重复跑 LLM。`user_limit` 只限制进入本次批次的用户数，`limit_per_user` 限制单个用户贡献的 watchlist 数量。`dry_run=true` 只返回 paid/entitled 用户 watchlist 并集，不触发生成。

2026-08-10 软退休并设为 inactive，不再自动触发。schedule、页面、API 与手动生成

`cron-trigger` job `watchlist_monitor_paid_universe` 最终调用
`/api/admin/watchlist-monitor/start-paid-universe`。该端点在 Railway 进程内启动

## 数据流

```
Cron/Admin generate
  -> resolve_symbols_for_generation()
     -> explicit symbols OR brew.db.get_user_watchlist(user_id)
  -> _load_common_inputs()
     -> get_batch_quotes() for ticker quotes + market/sector proxy quotes
     -> get_earnings_calendar()
     -> get_economic_calendar()
     -> FMP sector performance snapshot
  -> build_ticker_context()
     -> get_technical_data()
     -> deterministic technical_monitor detector
        -> only registers technical_1 source when technical data is available
     -> compact market_context for background-aware analysis
     -> get_fmp_news(symbol)
        -> enrich with one Tavily `{TICKER} stock news` search
        -> merge/dedupe FMP + Tavily news before LLM input
     -> deterministic event_candidates from earnings and macro calendar inputs
     -> compact source_refs
  -> build market_discussion cache
     -> twitter.db.list_ticker_discussion() reads cached kol_tweets only
     -> build deterministic theme groups, then rewrite overview/theme summaries
        from evidence tweets through discussion_summary_agent.py
     -> compact overview/themes are attached to final brief context
  -> ticker_brief_agent.generate_ticker_brief()
     -> DeepSeek direct API JSON Output split subtasks
        -> news_events_synthesis / technical interpretation / market discussion run concurrently
     -> final brief composition (headline/ai_take/signals only)
     -> local Pydantic validation + retry per small schema
  -> quality gate
  -> upsert ticker_daily_briefs via watchlist-monitor Edge Function

Cron test-universe generate
  -> generate_test_user_universe()
     -> load Voya + owner watchlists, or explicit admin-provided user_ids
     -> normalize + dedupe symbols into one ticker universe
     -> dry_run=true returns universe only
     -> dry_run=false calls generate_for_symbols(universe, force=false)
     -> existing same-day briefs are skipped by generate_for_symbols()

Cron paid-universe generate
  -> generate_paid_user_universe()
     -> list_users_with_entitlement("for_you_website")
     -> load each entitled user's watchlist
     -> normalize + dedupe symbols into one paid ticker universe with no ticker cap
     -> dry_run=true returns universe only
     -> dry_run=false calls generate_for_symbols(universe, force=false)
     -> existing same-day briefs are skipped by generate_for_symbols()

User backfill
  -> POST /api/watchlist-monitor/backfill
  -> verify_user_token + require for_you_website entitlement
  -> resolve_missing_symbols_for_user_backfill()
     -> load current user's watchlist only
     -> read latest ticker_daily_briefs for that watchlist/request subset
     -> queue only symbols with no current brief, stale brief, or missing market_discussion cache
  -> BackgroundTasks calls generate_for_symbols(queued_symbols, force=false)

User read
  -> GET /api/watchlist-monitor
  -> verify_user_token + require for_you_website entitlement
  -> brew.db.get_user_watchlist(user_id)
  -> read latest ticker_daily_briefs
  -> mark rows stale unless brief_date == current market date, while preserving latest cached brief content
  -> compose summary / ticker_rows / watchpoints
  -> return; no LLM call and no Twitter discussion summary call
```

## 数据契约

### `ticker_daily_briefs`

一行是一只 ticker 在某个 market date 的共享日更分析。

核心字段：

- `symbol`
- `brief_date`
- `model_version`
- `headline`
- `ai_take`
- `signals` JSONB
- `watchpoints` JSONB
- `event_candidates` JSONB：未来 14 天公司相关事件、社交观察点和宏观背景 candidates
- `market_discussion` JSONB：离线生成的市场讨论 tab payload（overview、themes、原文样本），形状与 `GET /api/twitter/ticker-discussion` 响应一致
- `source_refs` JSONB
- `generated_at`

`event_candidates` 保存在 brief JSON 中，保证用户读取路径只读 cached brief，不额外查询历史事件表。

`source_ref_ids` 的合法性定义：任何 signal、watchpoint、event candidate 引用的 source id 必须出现在同一条 brief 的 `source_refs[].id` 里。当前生成路径会注册这些 id：

- `quote_1`：当前 ticker quote snapshot。
- `technical_1`：规则生成的技术面 snapshot。
- `market_1`：市场/板块 benchmark quote snapshot。
- `news_1` ... `news_15`：FMP + Tavily 合并去重后的新闻源。
- `earnings_1` ... `earnings_3`：FMP 财报日历。
- `macro_1` ... `macro_5`：核心宏观日历事件。
- `market_discussion`：后台从 cached `kol_tweets` 生成的 ticker 市场讨论 summary/themes，可被 final brief 作为“市场讨论/分歧”来源引用，但不能当成已验证公司事实。

### `ticker_rows`

`GET /api/watchlist-monitor` 的 `ticker_rows` 是 Workbench 主视图使用的轻量详情 payload。每个 row 会带：

- ticker 主判断：`headline`、`ai_take`；是否过期由 `is_stale` 派生，不保存业务 status 或排序分数字段
- 新闻总结：`news_summary`，由过去 7 天最多 15 条英文新闻压缩为中文基本面/事件解读
- 技术盯盘：`technical_monitor`，包含用户可读的 `technical_view`、简短现状总结、关键价位和 deterministic 硬信号
- 列表聚合字段：`signal_types`、`top_signal`、`next_watchpoint`
- 详情视图字段：完整 `signals`、`watchpoints`、`source_refs`
- 未来事件字段：`event_candidates`
- 市场讨论字段：`market_discussion`，由后台生成阶段读取 cached `kol_tweets` 并生成中文 overview/themes，前端只读该缓存字段；`overview.one_line_summary` 和 `theme.summary` 是主要可读出口，应总结讨论方式、观点逻辑链、具体分歧和待验证变量，而不是只复述样本量和情绪

前端 `/for-you/monitor` 依赖这些详情字段渲染单 ticker 的 summary、新闻、技术面、社交讨论、未来事件、财报、资金流和分析师评级分区。读取路径仍然只读 cached briefs，不允许触发 LLM。

`technical_monitor` 是监控页专用字段，不复用 `/stock/[symbol]` 个股页的技术分析 agent。它由 `signal_builder._build_technical_monitor()` 基于 `shared/data_tools/technical.get_technical_data()` 的 OHLCV / indicators / derived / support_resistance 数据生成：

- `summary`: 一段简短中文现状总结，描述趋势、RSI/MACD 动能、关键价位和今日硬信号；不输出买卖建议。
- `technical_view`: 面向 Workbench 技术面 tab 的解释层，由规则生成而非 LLM。主展示契约是 `regime`、一段较完整的 `verdict`，以及趋势/动能/位置/波动四个维度；`verdict` 会把四个维度压缩成一段用户只读一眼也能理解的技术面判断。动能维度必须显式覆盖 RSI 与 MACD；波动维度必须覆盖布林带和成交量。
- `key_levels`: current price、支撑/阻力、20/50/200 日均线、Bollinger 上下轨。
- `signals`: 可复核的硬信号，最多 12 条，包括 20 日突破/跌破、假突破/假跌破、均线站回/跌破、50/200 金叉死叉、均线多空排列、放量上涨/下跌、缩量上涨、RSI、MACD、Bollinger、5 日急涨急跌、接近支撑/阻力。

## Brief 生成原则

- 每个 ticker 的主输出是一段 `ai_take`，不是多个碎片卡片。
- `ai_take` 目标长度为 220-360 个中文字；它应综合新闻/事件中间结论、技术解释、市场背景和 `market_discussion`，而不是只给一句快速判断。
- `ai_take` 只总结发生了什么和接下来观察什么，不输出买入、卖出、加仓、减仓、持有等操作建议。
- 新闻和未来事件由同一个 `news_events_synthesis` LLM pass 处理：输入包括 rolling 7d 英文新闻、deterministic event candidates（财报/宏观）和 market context；输出 `news_summary`、从新闻抽到的 `news_event_candidates`、最终用户可见 `watchpoints` 和内部 `debug_notes`。`news_summary` 不是标题列表，应覆盖事实变化、基本面/估值影响通道、尚未验证的信息和后续验证点，确保 final composition 可以直接读取中间结论而不需要重读 raw news。这样同一个 FOMC/财报/会议不会分别被新闻总结、事件抽取和 final composition 重复生成。新闻输入会同时取 FMP ticker news 和 Tavily `{TICKER} stock news`，合并去重后一起传给 LLM。
- `news_events_synthesis` 同时返回 `translated_news_titles`，后端只把 `news_*` source 的中文标题写入 `source_refs.title_zh`。原始英文标题仍保留在 `source_refs.title`，URL 仍指向原文。
- 新闻输入用于抽取 `news_event_candidates`：LLM 只能从 `news_items` 中抽取未来 14 天内的公司相关事件；没有明确日期时必须使用 `event_date=null`、`date_precision=unknown`、`status=tentative`，不能编造日期。`news_event_candidates` 必须是 company-specific，且只能引用 `news_*` 来源，不能复制 macro calendar、deterministic event candidates 或 technical signals。
- 未来事件不是所有观察点的堆叠：公司事件优先；宏观只保留对成长股估值环境有明确影响的核心事件（如 FOMC、CPI、PCE、就业、GDP/ISM），并把同日 FOMC 利率决议、经济预测、新闻发布会合并成一个事件包；低相关宏观数据（如 Housing Starts）不进入 ticker 未来事件。
- 技术面硬信号只保留在 `technical_monitor` 和技术面 tab，不再复制成未来事件。
- 技术面硬信号由规则检测生成，LLM 只解释 compact input，不负责判断这些硬信号是否存在。
- 技术面 compact input 会额外携带最近最多 8 个交易日的 `recent_price_path`（收盘价、逐日涨跌、连续上涨/下跌计数、相对近期高低点变化）。技术解释和最终 `ai_take` 必须用它复核“连续下跌/持续走弱/反弹后回吐”等走势语言，不能只根据 5 日/20 日汇总涨跌推断价格路径。
- 生成分析必须 market-aware：`market_context` 会把 SPY/QQQ/IWM、sector ETF、SMH/TLT/USO 等市场代理、sector snapshot、ticker 相对大盘/板块的当日表现传给 LLM。前端不显式展示“市场背景”板块，LLM 只在 `ai_take` / `news_summary` 里自然说明大盘或板块背景。
- `market_discussion` 会在 `generate_ticker_brief()` 前构建；final brief 只接收压缩后的 overview/themes，不接收 raw tweet 列表。讨论摘要生成会用 evidence tweets/key_claim/quoted text 改写现有 overview/theme 文案，但不会扩展复杂 API schema；失败时回退确定性模板。它只能作为“市场讨论/分歧”输入，不能当作已验证公司事实。Watchlist monitor pipeline 不再读取 Twitter Digest 的 ticker thesis、hot tickers 或 watchpoints。
- 不做假精确归因：除非输入里有直接证据，LLM 不应写“上涨主要来自 X”或百分比归因；应使用“处在科技股整体反弹背景下”“公司新闻提供额外催化”“不应完全归因于单一公司新闻”等审慎表达。
- LLM 只使用 compact input JSON，不直接吃原始大文本。
- Ticker brief LLM 使用 DeepSeek OpenAI-compatible `/chat/completions` 直连接口和 `response_format={"type":"json_object"}`，并显式设置 `thinking={"type":"disabled"}`，避免 V4 默认 thinking 消耗输出 token 导致 content 为空。DeepSeek JSON Output 只保证合法 JSON，不保证严格 JSON Schema；本地按子任务使用小 Pydantic schema 校验并 retry：`NewsEventsSynthesisOutput`、`TechnicalInterpretationOutput`、`MarketDiscussionOutput`、`BriefCompositionOutput`。最终再合成为 `TickerBriefAgentOutput` 交给 `service.py` 质量门。官方 `/models` 当前只返回 `deepseek-v4-flash`、`deepseek-v4-pro`，没有 `deepseek-v3-pro`；若未来有私有模型 ID，可用 `WATCHLIST_MONITOR_LLM_MODEL` 覆盖。
- Dated watchpoint 必须有 `date` 和 `source_ref_ids`。
- Event candidate 的 `source_ref_ids` 必须能在 `source_refs` 找到；生成 pipeline 会过滤未来 14 天窗口外的 exact-date candidates，并按 `dedupe_key` 去重。
- 生成后的 cleanup 会把已由 `event_candidates` 覆盖的 dated watchpoints 过滤掉，也会删除重复未来事件的 `event` / `macro_sector` signals。
- 保存质量门会拒绝：空 headline/ai_take、无法回答“今日信号/影响/接下来”的 `ai_take`、新闻源存在但 `news_summary` 为空、技术源存在但 `technical_monitor.summary` 或 `technical_view.verdict` 为空、直接操作建议措辞（如“建议买入/卖出”“追高”“不宜”等）。机构评级或已发生的投资人买卖动作可以作为事实引用，但不能写成给用户的操作建议。
- 读取路径按 `brief_date` 判断新鲜度；只要不是当前 market date，行级 `is_stale` 会设为 `true`，但仍保留最近一次 brief 的 headline、ai_take、新闻、技术面、信号、source refs 和 row-level event candidates，作为“昨日/上次监控”回退展示。旧 brief 不计入 new signals、全局 future events 或 freshness。完全没有 brief 的 ticker 才返回“今日监控尚未生成”的空占位。
- LLM 失败或质量门失败不能写 fake success。
- `news_events_synthesis`、`technical_interpretation`、`market_discussion`、`final_brief` 子任务都有明确超时；新闻合成 JSON 失败或返回英文摘要时，会使用确定性中文主题 fallback；final brief 失败时，会基于已收集的 news/technical/market-discussion/event 输入生成保守 fallback。
- 不输出买卖建议。

## 当前 V0 数据源

- FMP quote/news/earnings/economic calendar。新闻输入固定使用 rolling 7d，最多传 15 条。
- Tavily Search API：仅用于 watchlist monitor 生成路径的默认新闻源之一。每次生成 ticker brief 都会在 FMP 之外调用一次 Tavily，固定使用 `{TICKER} stock news` 查询最近一周新闻，并限定在一组金融新闻/行情域名中。读取路径不调用 Tavily。
- FMP benchmark/theme quote proxies：SPY、QQQ、IWM、DIA、sector ETFs、SMH、TLT、USO，用于后台 market-aware 分析，不直接作为前端板块展示。
- FMP sector performance snapshot，用于判断个股所处 sector 是否顺风/逆风。
- `shared/data_tools/technical.py` 技术面摘要与监控页 `technical_monitor` 图表/硬信号。
- `kol_tweets` 近期缓存：仅在后台生成时读取，用于 `market_discussion`；用户打开页面或切换 tab 不再调用 `/api/twitter/ticker-discussion` 生成摘要。Watchlist monitor pipeline 不再读取 `twitter_digest` 成品中的 ticker thesis、hot tickers 或 watchpoints。

## LLM 配置

- `WATCHLIST_MONITOR_LLM_MODEL`: 默认 `deepseek-v4-pro`。
- `WATCHLIST_MONITOR_LLM_MAX_TOKENS`: 默认 `2400`。
- `WATCHLIST_MONITOR_LLM_RETRIES`: 默认 `2`。
- `WATCHLIST_MONITOR_LLM_TEMPERATURE`: 默认 `0.2`。
- `WATCHLIST_MONITOR_MODEL_VERSION`: 默认 `watchlist-monitor-v1-{model}`，写入 `ticker_daily_briefs.model_version`。
- `WATCHLIST_MONITOR_GENERATION_CONCURRENCY`: 默认 `3`；限制同一批次中同时生成的 ticker 数，避免 FMP/Tavily/DeepSeek 请求放大。
- `WATCHLIST_MONITOR_TAVILY_ENABLED`: 默认 `true`；没有 `TAVILY_API_KEY` 时自动跳过。
- `WATCHLIST_MONITOR_TAVILY_RESULTS_PER_QUERY`: 默认 `8`。
- `WATCHLIST_MONITOR_TAVILY_TIMEOUT_S`: 默认 `8.0`。
- `WATCHLIST_MONITOR_TAVILY_TOPIC`: 默认 `general`。Tavily 的 `news` topic 对股票 ticker 查询噪声较大，当前默认用 general + 金融域名白名单。
- `WATCHLIST_MONITOR_TAVILY_INCLUDE_DOMAINS`: 默认包含 MarketBeat、TipRanks、TradersUnion、StocksToTrade、SimplyWall、StockTitan、Seeking Alpha、Investing、Yahoo Finance、Barchart、Benzinga。

## 并行化与服务限制研究

当前生成链路有两层并行：

- 批次层：`generate_for_symbols()` 对 ticker 使用 `WATCHLIST_MONITOR_GENERATION_CONCURRENCY` 做有界并发，默认 3。单个 ticker 失败只进入 `failed`，不会取消整批。
- 单 ticker LLM 层：`generate_ticker_brief()` 内的 `news_events_synthesis`、`technical_interpretation`、`market_discussion` 三个互不依赖的 DeepSeek 子任务并行执行；`final_brief` 仍等待三者完成后再组合。

服务限制依据：

- DeepSeek 官方限制是 account-level concurrency，不是固定 RPM：`deepseek-v4-pro=500`、`deepseek-v4-flash=2500`；超过并发返回 HTTP 429。一个请求从发送到模型响应完成都算占用并发。当前默认 3 个 ticker 并发，单 ticker 最多 3 个前置 DeepSeek 子任务同时跑，因此常规峰值约 9 个 DeepSeek 并发，远低于官方上限。客户端会对 429/5xx 做小次数重试并尊重 `Retry-After`。来源：https://api-docs.deepseek.com/quick_start/rate_limit/
- Tavily `/search` 官方限制：Development key 100 RPM，Production key 1000 RPM；超限返回 429 且带 `retry-after`。本 pipeline 每个 ticker 固定 1 次 basic search。默认 3 个 ticker 并发时，Tavily 短时并发通常不超过 3 个同步查询，25 个 ticker 的总 Tavily search 上限约 25 次；100 个 ticker 是 100 次 search / 100 credits。来源：https://docs.tavily.com/documentation/rate-limits
- FMP 官方 pricing 暴露不同 plan 的调用上限：Basic 250 calls/day，Starter 300 calls/min，Premium 750 calls/min，Ultimate 3000 calls/min。生成链路已把 quote、earnings、economic calendar、sector snapshot 做批次级共享，但 per-ticker context 仍会调用 profile/news/technical 相关 FMP 数据，因此默认 ticker 并发保持保守。来源：https://site.financialmodelingprep.com/developer/docs/pricing
- InsForge Edge Functions 官方定位是 request/response 和 short-lived jobs；需要常驻 worker 或长任务时应使用 Compute。当前重型生成仍在 Python backend/admin endpoint 内执行，Edge Function 只负责 `latest_briefs` 读取和 `upsert_brief` 写入，避免把长 LLM pipeline 放进 Edge Function。来源：https://docs.insforge.dev/core-concepts/functions/overview

暂不接入 SEC/IR crawling 或实时 signal stream。

## 注意事项

- `GET /api/watchlist-monitor` 是缓存读取路径，不允许触发重型 LLM。
- `POST /api/watchlist-monitor/backfill` 是用户级补洞入口，只补当前用户 watchlist 中缺失/过期/缺讨论缓存的 ticker；不要把它改成 paid universe 或全市场 backfill。
- Admin generate endpoint 支持显式 symbols、单个 `user_id` watchlist、Voya + owner test universe，以及所有 `for_you_website` entitlement 用户的 paid universe。生产 public cron 应使用 `/api/admin/watchlist-monitor/generate-paid-universe` 或 `cron-trigger` 的 `watchlist_monitor_paid_universe` job；paid universe 按全量去重 ticker 生成，`get_latest_briefs()` 会分批读取缓存以覆盖 50 个以上的 symbol。
- Social signal 只解释社交平台讨论，不作为事实来源。
