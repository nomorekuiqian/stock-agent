# Railway 资源优化复核

日期：2026-10-13，Asia/Taipei。本轮为只读审计，未修改代码、资源限制、套餐、调度或部署，未重启生产。

**判断：有明确的内存优化点。第一优先是清理一次性 AI 任务的临时会话，其次减少已暂停模块的启动加载。继续压 CPU 或增加副本都不符合当前负载。**

## 优先级一：一次性任务的会话没有释放

已经对照线上源码确认，非仅查看本地未提交版本：

1. `twitter_digest/agents.py` 的 `_runners` 全局字典保留 InMemoryRunner。
2. `twitter_digest/enrichment.py:138` 每批创建新 session，执行和读取结果后没有 `delete_session`；`service.py:371` 的日报编排存在同样模式。
3. `brew/agent.py:452` / `455` 创建常驻 runner，`get_personal_digest()` 返回全局单例；`:772` 每次生成新建 session，也没有清理。
4. 生产安装的 ADK `InMemorySessionService` 用字典保存 session，创建时加入字典、删除时才移除；所查实现没有自动 TTL 或数量淘汰。

这是一条明确的会话积累路径，运行越久会保存越多历史输入、输出和事件。10 月 1–12 日 enrichment 记录 1,773 次模型调用、个人日报 245 次；调用数不是现场堆中 session 数，但说明这不是低频路径。

**建议修复：** 对一次性任务建立完整生命周期，在结果提取完毕后，成功、异常和取消路径均清理临时 session；先保证结果已脱离临时状态，再释放。清理对象是进程内一次性会话，不是数据库中的正式日报或用户聊天历史。

早报、晚报和周报源码也存在 create_session 后未显式删除的模式，应一起检查 runner 是否长期复用。已有清理的用户研究/对话路径不应机械重写。

验证应使用离线 fake runner，覆盖成功、失败、取消及多次执行后会话数不增长；部署后看正常任务运行时的内存曲线。当前未抓取生产堆，不能断言全部 1.5 GB 都由 session 引起，也不能承诺修复后具体降到多少。

## 优先级二：已暂停功能仍占启动资源

生产 `main.py` 仍无条件导入多个已暂停模块，并创建 FastMCP 应用、启动它的 lifespan、挂载 `/frank`，之后才由暂停中间件限制访问。

可按暂停状态跳过专属模块的初始化或按需导入，保留代码和数据。需要保留 Frank / Serenity 已恢复的对话依赖，不能把整个 `kol_research` 包一刀切删除。该项潜在收益尚未单独测量。

当前业务会用到 pandas / yfinance 等依赖。删除 Docker 中未运行的 gcc、测试库，主要缩短构建并减少镜像体积，不会自动等比例减少常驻 RAM 账单，应排在运行时修复之后。

## 暂不建议的做法

| 做法 | 原因 |
|---|---|
| 直接把内存上限压到 512 MB / 1 GB | 当前进程已超过，可能 OOM；资源上限不是预购容量，调小不会直接降低实际内存使用 |
| 增加 worker / 拆出一个常驻 cron 服务 | 会复制 Python、ADK 及数据处理库的常驻内存；当前 CPU 很低，没有证据需要增加副本 |
| 用定时重启替代清理 | 可暂时回收积累内存，但可能中断生成/流式对话，且不能修复持续积累的原因 |
| 现在直接开启 Serverless | 需新部署才生效，空闲判断受外部通信影响；每小时任务和用户请求会唤醒，首次访问有冷启动甚至 502 风险，先修内存更稳妥 |
| 调低硬性月支出上限作为降本 | 超额会停服务，是风险控制而不是单位资源优化 |

注意：活动统计循环每 30 秒检查一次，但空队列会直接返回，不能仅凭循环频率断言它一定阻止休眠。Langfuse/PostHog 导出是否持续阻止休眠需测量实际流量。

## 节省尺度

Railway 当前 RAM 单价为 $10/GB/月，按实际用量计费。因此持续降低约 0.1 GB 平均内存，约对应 $1/月资源费；降低 0.5 GB，约 $5/月。**这是价格换算，不是修复效果预测。** Hobby 最低 $5/月，低于底价后再降用量不会同比减少付款。

建议顺序：先修一次性 session 清理 → 查看修复后的内存基线与增长速度 → 再做暂停模块按需加载 → 最后决定是否值得评估休眠。对当前规模，不建议先引入额外常驻服务或平台迁移。
