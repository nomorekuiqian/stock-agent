## 1. 产品要收敛成什么

**用户告诉我们持有什么；服务持续检查相关信息，解释新变化为什么与他有关。**

建议第一版服务中文美股/ETF 持有者，默认每个美股交易日盘后处理一次；这是沿用现有产品的范围假设，尚未完成用户研究。核心结果是「几分钟知道自己需要知道的事」。让用户主动提供标的即可获得第一份结果，数量、成本、持有理由后补。

成功不等于用户每天打开很多页面：用户读完一两条便离开，也可以说明服务完成了任务。网站承担设置、阅读、查证和历史；邮件承担交付；Agent 在后台完成筛选。

推荐先做 A，B、C 是替代路线。不要把三个方案合并成更多导航和功能。

## 3. Taste：从现有视觉中保留什么、改变什么

已观察的参考是用户自己的公开首页，未假称使用外部参考站。当前画面有暖黑底、绿色主按钮与标题、居中大标题、大量首屏留白、模糊绿色/棕色背景光。新方向 A/B/C 中未经用户挑选的偏好，均视为提案，而非用户已确认审美。

| 维度 | 可见证据 | 可迁移规则 | 本轮约束 |
|---|---|---|---|
| 明暗/光线 | 暖黑页面上存在柔和背景光 | 用明暗分层建立焦点 | 工作页移除装饰性光斑；不把光晕等同高级感 |
| 色彩 | 绿色集中在品牌、标题和主 CTA | 全屏只设一种主要品牌强调色 | 绿色代表选中/主动作；重要性用文字 + 小面积琥珀色，不能混同涨跌 |
| 材质 | 当前主体基本是平面，背景有柔和渐变 | 保留平面、低装饰表达 | A 用纸色不做纸纹噪点；B 用白底；C 用哑光深色 |
| 空间 | 居中 Hero 占满首屏，结果需下滚才接近 | 每个屏幕一个主要焦点 | 工作页焦点给当天最重要的变化，首屏直接可读结果 |
| 氛围/张力 | 书写感大标题配理性的导航和小字 | 品牌标题可有性格，正文保持易读 | 中文正文 16–18px；不把手写字体扩展到报告全文 |

参考分工：现有首页负责品牌色与克制程度；当前设计规范负责中文字体、数字排版和主题约束；用户本次任务负责信息层级和功能删减，优先级最高。三个方案的布局是本轮原创提案。

结构化文件：taste-profile.json 与 design-signal-packet.json（位于同名 assets 目录）。

## 4. 三个 UI 方案

### A. 持仓简报 — 推荐

体验像收到一封排版很好的私人简报。适合用户每天花 2–3 分钟确认变化，也最容易复用于邮件。

- 暖白 #F7F5EF，墨色 #242821，深绿 #176B52，细分隔线 #DDDCD4。
- 桌面主内容宽约 1120px：760px 阅读栏 + 240px 持仓/未来事件旁注；不是一屏等权卡片。
- 顶部「今天有 2 件事值得看」+ 本次检查时间；2–3 个按重要性排列的事件，每条默认 60–100 个中文字。
- 事件顺序固定为「发生了什么 / 为什么与你有关 / 下一步观察什么 / 来源」。
- 大标题可用宋体或现有 editorial 字体；正文用现有 system UI；数字、日期、ticker 用等宽字体。
- 来源详情展开，追问是事件末尾的次动作，默认没有空白聊天框。
- 手机改单列，先简报，后持仓摘要；持仓录入用独立全屏表单。顶部三导航可缩为底部三项，设置留账户菜单。
- 代价：信息密集用户会希望更快按股票筛选；可加轻量 ticker 筛选，不新增完整工作台。

### B. 重要信息收件箱

体验像邮件收件箱：左侧导航，中间事件列表，右侧阅读详情。适合持仓较多、需要标记已读和追问的用户。

- 近白 #FAFBFA、墨黑 #18231E、绿色 #147D5A、细线 #E5E9E6。
- 桌面约 176 / 360 / 650px 三栏；选中行用细绿色边线和浅底，右侧正文保持 16–18px。
- 按「值得留意 / 已读」筛选；事件级「有帮助 / 不相关」反馈。
- 手机只保留列表，点入详情并提供返回；不把三栏压缩成小字。
- 代价：要维护已读、筛选、详情恢复、反馈状态，交互成本高于 A；避免未读红点制造清空压力。
- 适用条件：试用者确实需要一次处理多个独立事件，且愿意反馈，不只是觉得收件箱外观漂亮。

### C. 持仓观察台

体验围绕股票列表：左侧看哪只持仓有变化，右侧解释该变化。适合更专业、按 ticker 逐只检查的人。

- 暖黑 #121611、深灰绿 #1B211C、浅字 #EEF2E9、低饱和绿 #7AC5A6。
- 55% 持仓表 / 45% 证据详情；表列控制为 ticker、权重、信息变化、最近检查。
- 下方只有未来一周的相关事件，不添加大盘热力图、资产收益图或交易操作。
- 手机持仓表转简短列表，详情独立进入，避免横向滚动才能理解内容。
- 代价：用户容易把它理解成实时盯盘工具，后续也最容易长出新功能；与轻运营目标匹配度最低。
- 适用条件：存量付费用户主要价值确实在逐股检查，并且批次更新的时效已满足需要。

### 所有方案共用的关键页面

**未登录首页**：品牌 +「持仓相关的重要信息，替你筛出来」；唯一主按钮「添加我的持仓」，次链接「看看简报示例」。首屏真实大小预览一份短简报。下方只留三步说明、覆盖范围/更新节奏、收费与 FAQ。用户数、覆盖数、创始人职业描述需重新核实，不能机械继承旧文案。

**持仓录入**：输入/搜索 ticker → 确认为「已持有」或「仅关注」→ 立即看样例/首次结果。权重、持有理由可后补；不强制填成本、目标价、止损价和整份风险问卷。未填权重显示「未提供」，不可冒充真实等权持仓。保留更新时间及「持仓没变」快捷确认。

**事件详情**：证据链接、发布时间、抓取/检查时间、关联的真实持仓、推断与事实分开；“为什么与你有关”必须可被审阅。追问默认只围绕该事件与相关持仓展开。

**历史/设置**：历史是一条日期列表，支持按 ticker 找回。设置统一账户、持仓、邮件频率、付费、取消订阅；邮件退订和支付取消含义不同，入口需写清楚。

### 必须设计的六种状态

1. 没有持仓：只解释第一步，并提供可辨识的示例；不显示空报表。
2. 首次处理中：显示检查范围和更新时间预期，可离开；不显示伪造进度百分比。
3. 有重要变化：默认 1–3 条重点，但关键事件超过 3 条时显示全部重要事件或明确「另有 N 条」，不可为短而漏报。
4. 没有重要新增：「已完成本次检查；在已覆盖信息中未发现重要新增。」检查状态不冒充收益安全。
5. 数据部分失败：例如「8 只持仓中，2 只本次未完成检查」；失败标的不能写「无事发生」。
6. 旧结果/持仓过期：显式标注日期、待更新状态和持仓最近确认时间。

基础验收：390 / 768 / 1440px 无信息截断；正文对比度至少 4.5:1，重点状态不只靠颜色；键盘可达、触控目标至少 44px；减少动态效果设置生效。只实施一个方案，继续使用现有组件/字体基础。

## 5. 其余模块的不同方向

### 5.1 持仓录入

| 方向 | 能力 | 好处 | 代价/边界 |
|---|---|---|---|
| 轻录入（推荐首版） | ticker + 持有/关注状态；权重、理由选填 | 第一份结果快，维护最少 | 需要明确未知权重，改掉现有 ghost 语义冲突 |
| 导入优先 | 手动 + 已有截图识别 → 逐行确认 | 10 只以上更省事，可复用既有代码 | 识别失败、旧持仓替换、重复 symbol 都需要确认流程；先不扩 CSV/PDF |
| 券商同步 | 自动同步数量与变动 | 长期最省用户操作 | 接入覆盖、连接失效、外部费用与客服负担；等真实需求再立项 |

用户持有的证券与仅关注证券必须在数据上有明确状态；不能因为 UI 被放到「我的持仓」就假定全部真实持有。旧用户 symbol-only watchlist 迁移为「仅关注」，不自动推断为持仓。

### 5.2 信息筛选

| 方向 | 筛选依据 | 好处 | 代价 |
|---|---|---|---|
| 标的相关新闻 | ticker/公司别名、时效、去重 | 最快落地，可做低成本基线 | 容易退化成新闻摘要，不能充分说明个性化 |
| 持仓影响排序（推荐） | 事件重要性 + 持仓关联 + 新增程度 + 已知权重/偏好 | 兼顾可理解价值和工程规模 | 需要事实结构与可解释排序，不用伪精确分数对用户展示 |
| 持有理由变化 | 新事实支持/削弱/尚不能判断用户记录的理由 | 差异化更强，噪音更少 | 要有真实理由、持续证据及反例评测；不能每天硬判“逻辑未破” |

首版推荐第二种，理由是可选增强。泛宏观只在存在具体传导路径时进入持仓简报；同一个利率事件影响三只股票时只出现一次。KOL 作为可选观点来源，明确观点身份，不能替代事实验证。

### 5.3 交付节奏

| 方向 | 用户收到什么 | 运营特征 |
|---|---|---|
| 每日一次（推荐） | 每个交易日盘后网站更新；邮件是否发送由用户频率偏好决定 | 最容易承诺和验证；无事件也留检查记录 |
| 仅重要事件 | 批次检查后有重要新增才发，另可选周回顾 | 降低邮件噪音；要避免用户把安静误解为系统停了 |
| 盘中提醒 | 重要事件尽快到达 | 时效、误报、数据许可、值班要求明显提高，首版不做 |

建议产品承诺用「每个美股交易日盘后检查」，初始工程目标可试收盘后 60–90 分钟内完成，需先测当前数据延迟与任务耗时。只做批次服务时，不宣传“实时”。

### 5.4 Agent 与模型

| 方向 | 具体做法 | 合适阶段 |
|---|---|---|
| 最小升级 | 专属日报迁到项目标准 gemini-3.5-flash；重写长文 prompt；输出结构保持尽量兼容 | 先获得可靠基线，实施成本最低 |
| 共享事实 + 个性化筛选（推荐目标） | 公共事件提取一次并缓存；规则匹配用户；模型只解释重点；可仍使用同一个模型 | 在质量与长期成本之间最合适 |
| 跨模型对照/高难问题复核 | 用当前模型与另一可用模型盲评；仅把实测有收益的任务分流 | 后续阶段，不默认维护多供应商和多 Agent 辩论 |

项目 AGENTS.md 当前默认 Google ADK 模型为 gemini-3.5-flash。Google 官方确认该 model ID 为 stable 且支持结构化输出；这里将其作为项目升级基线，而非声称它必然是最新或效果最好的模型。采用其他默认模型应同时明确更新项目约定。

- 官方模型资料：https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash
- 官方结构化输出：https://ai.google.dev/gemini-api/docs/structured-output

**不能把换模型当成完成升级。** 同时处理输出目标、事实可追溯、缺失数据、去重、超时、语义缓存和评测。

### 5.5 收费与服务范围

| 方向 | 形态 | 判断 |
|---|---|---|
| 免费样例/短试用 + 一个付费套餐（推荐） | 按持仓覆盖上限和交付节奏收费 | 最容易讲清楚，也减少权限分叉 |
| 小额基础版 + 深度版 | 短简报与按需追问分层 | 适合已经观察到明显使用差异后 |
| 保留多档 + 博主/社群包 | 沿用现有多产品销售 | 能保留旧商业关系，但不适合继续扩大为主站结构 |

先沿用存量账单和已售权益；新套餐只作为试点产品，不自动给老用户迁价或删权。若某项合作有明确合同/付费承诺，作为隔离入口继续履约或另行沟通，不在 UI 清理时顺带关闭。

测试价格建议先与现有基础档接近，而不是直接涨价：例如将 $10/月作为访谈/付费试点锚点。这是测试假设，不是市场估值或改价决定。最终价格由数据/API/邮件/模型成本和续用意愿共同决定。

## 6. 功能减法清单

| 处理 | 模块/能力 | 具体方式 |
|---|---|---|
| 保留并提升为主线 | portfolio、brew、notification、sources、历史、反馈 | 围绕同一个事件/日报结果贯通 |
| 保留后台基础 | auth、subscription/payment/webhooks、退订、entitlement、成本计量、管理/失败记录 | 用户少看入口，运营仍需要 |
| 合并 | watchlist 与 portfolio 的管理入口 | 一个页面内明确持有/关注；数据库迁移另做计划，历史保持可读 |
| 合并 | 个股详情、追问 | 先变为事件详情内入口；成熟实现可以暂时复用 |
| 降为背景数据 | 通用日报、宏观、KOL 观点 | 有持仓关联才进入简报，不要求用户阅读多份独立日报 |
| 优先候选退出主导航 | 独立 Research、KOL 研究室、宏观仪表盘、持仓健康评分 | 用近 30/60 天使用与付费关联决定是否停生成；未核实前是候选 |
| 暂停新增投入 | 新市场覆盖、多账户券商同步、开放知识库、复杂画像、What-If、实时提醒 | 不放进首版 |
| 暂存兼容 | 旧 URL、旧报告、已购买的合作服务 | 读历史/重定向/隔离访问，而非直接删表 |

减法有两个层次：删入口降低用户认知负担；停无人依赖的定时生成降低成本。只删导航不会自动节省后端开销。

退出順序：审计页面使用和实际付费承诺 → 停推广/新增销售 → 对相关用户明确迁移安排 → 按依赖停定时任务 → 保留历史访问和回滚路径 → 再清代码。此轮只出方案，不执行停服。

## 7. 推荐目标架构

```text
用户明确的持有/关注 + 可选权重/理由
                    |
公共事实采集 -> 公司/事件消歧 -> 去重 + 版本化事实库
                                     |
                            用户相关性匹配与排序
                                     |
                           重点解释 + 结构校验
                                     |
                    一个结果版本 -> 网站 / 邮件 / 历史
```

- 只针对所有有效服务用户的去重标的集合处理事实；宏观事件做一次公共采集后映射。
- 缓存公共事实，不能把个人持仓/理由混入跨用户共享缓存。
- 网页读取已有结果不触发整套生成；首次缺口由受控队列处理。
- 复用 watchlist_monitor 的来源、去重、缓存、质量门思路，不复活完整新闻/技术/KOL 三路工作台。
- 失败按标的隔离；最大重试次数和预算明确；任何失败不写成功内容。
- source 记录 published_at、observed_at、source_url、类型和可信等级。新闻文本只是待分析数据，不是 Agent 的指令。
- 来源匹配先用发行人/公司标识与 ticker 别名确认；ETF 不要求做全量持仓穿透，先覆盖基金本身及已知宏观暴露。
- shared_event_id + revision 区分转载和实质更新；派送去重包含 user_id、事件版本、channel 和投递状态。新尝试先查投递记录，不能重新生成后重复发送。
- 个性化结果 key 至少包含 user_id、持仓/画像版本、事实批次、model/prompt/schema 版本；理由改变要失效。共享模型别名会变化时另记录运行日期与供应商返回元数据。
- 保持 user_id 来自服务端认证；现有身份、权限和租户隔离不能因简化前端而移除。
- 全成本包括数据、搜索、模型、重试、邮件、基础设施和人工支持；不能只比较 token 单价。

Gemini Batch API 官方是标准交互成本的 50%，目标周转时间 24 小时，适用于离线评测/回填。不能因为便宜就用它承诺收盘后立即出报。来源：https://ai.google.dev/gemini-api/docs/batch-api

## 8. 新 prompt 的骨架

```text
任务：
根据给定事实与用户明确提供的持仓信息，找出自上次检查以来值得用户知道的新变化。

选择规则：
- 值得提醒的条件是实质新增 + 有可说明的持仓关联 + 足够可信的依据。
- 同一事件的转载合并；已有事件只有出现实质变化时再次提示。
- 无重大新增可以返回空事件列表，仍返回检查状态。
- 默认展示最多 3 条重点，所有达到关键级别的事件必须保留并明确展示。
- 股价变化本身不是因果证据，不能凭涨跌编造“有人抄底/担心财报”等原因。

每条事件：
发生了什么；为什么与该用户有关；是否影响他明确记录的关注点；
尚不能确定什么；后续什么可观察事实能验证；对应 source_id。

事实约束：
- 仅使用给定来源；不得生成不存在的 URL、数字、发布时间。
- 市场数据可能延迟/出错；检查时间、来源冲突和缺失信息必须保留。
- 未提供仓位或理由就标记未知；不能把默认值写成用户的真实情况。
- 数据失败与“没有重要新增”必须使用不同状态。
- 事实、模型推断、第三方观点分开。
- 不给买卖指令；不输出没有依据的安全保证。

文字：
中文短句；每条 60–100 字为目标，细节展开；不为了条数或字数添信息。
```

建议结构字段：check_status、coverage、as_of、events[]；事件包含 event_id/revision、related_symbols、priority、fact、relevance_reason、thesis_relation（unknown/unchanged/supported/weakened）、uncertainties、next_watch、source_ids。枚举成功并不证明事实为真；另做来源和关键数字校验。

## 9. 验证与继续/停止条件

以下都是拟定试点阈值，不是已测结果或行业标准：

- 先招募 5–10 位真实持仓用户，连续观察 2 周；优先现有用户，试用邀请另行确认后发。
- 不把邮件打开率作为核心证据。看首份结果是否读懂、第二周是否继续阅读/查证、是否评价相关、是否愿意继续付费。
- 做 50–80 个固定历史样例，至少覆盖平静日、重大财报、同事件转载、同事件新版本、多个持仓受同一宏观冲击、资料不足、symbol 歧义、未填权重、持仓变化、部分采集失败。
- 数据安全硬门：不得编造来源/关键数字，不得跨用户泄露；样例中过线也不等于真实世界零错误。
- 质量起点：人工标注关键事件召回率 ≥90%；被选重点中有用事件占比 ≥80%；平静日误报率 ≤10%。报告样本数和错误类型，不用一个总分掩盖漏报。
- 留存方向：至少半数试点用户第二周仍主动使用或能明确复述收获；至少 3 人愿意付费继续。样本小，只作为继续实验的信号。
- 运营方向：两周稳定期后，每周人工维护目标 ≤2 小时；变量成本目标 ≤收入的 20–25%，都需以实际计量确认。
- 如果用户只评价“排版更好”但不继续用，暂停追加 UI；优先修相关性。
- 如果保持质量需要每天人工审稿/救火，不加实时提醒，先缩小来源/标的/交付承诺。
